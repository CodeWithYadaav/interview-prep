2.1 SCOPING AND HOISTING

Q: Explain scoping and hoisting in JavaScript.

A: "JavaScript has three types of scope:

**1. Global Scope**: Variables accessible everywhere
**2. Function Scope**: Variables accessible within function (`var`)
**3. Block Scope**: Variables accessible within block (`let`, `const`)

**Hoisting** is JavaScript's behavior of moving declarations to the top during compilation.

Example:

console.log(a); // undefined (hoisted but not initialized)
var a = 10;

console.log(b); // ReferenceError: Cannot access before initialization
let b = 20;

greet(); // Works! Function declarations are fully hoisted
function greet() {
  console.log('Hello');
}


**Key Points:**
- `var` declarations are hoisted and initialized with `undefined`
- `let` and `const` are hoisted but stay in Temporal Dead Zone (TDZ)
- Function declarations are fully hoisted
- Function expressions are not hoisted"

2.2 PROMISES, CALLBACKS, ASYNC/AWAIT
═══════════════════════════════════════════════════════════════════════════════════════

Q: Explain the difference between Callbacks, Promises, and Async/Await.

A: "These are different ways to handle asynchronous operations:

**1. Callbacks** (Old way - callback hell):

getUserData(userId, (error, user) => {
  if (error) {
    console.error(error);
  } else {
    getOrders(user.id, (error, orders) => {
      if (error) {
        console.error(error);
      } else {
        // Nested callbacks - hard to read!
      }
    });
  }
});


**2. Promises** (Better - chainable):

getUserData(userId)
  .then(user => getOrders(user.id))
  .then(orders => console.log(orders))
  .catch(error => console.error(error));


**3. Async/Await** (Best - looks synchronous):

async function fetchUserOrders(userId) {
  try {
    const user = await getUserData(userId);
    const orders = await getOrders(user.id);
    return orders;
  } catch (error) {
    console.error(error);
  }
}


**When I use what:**
- Callbacks: Only when working with libraries that don't support Promises
- Promises: For multiple parallel operations (`Promise.all`, `Promise.race`)
- Async/Await: Default choice for better readability and error handling"

3.1 DIFFERENCE BETWEEN `any` AND `unknown`

Q: What's the difference between `any` and `unknown` in TypeScript?

A: "Both `any` and `unknown` can hold any type of value, but they differ in type safety:

**`any`** - Disables type checking:

let value: any = 'hello';
value.toUpperCase(); // Works
value.nonExistent(); // No error, but runtime crash!
value = 123;
value.toFixed(); // Works


**`unknown`** - Type-safe (requires type checking):

let value: unknown = 'hello';
value.toUpperCase(); // Error: Object is of type 'unknown'

// Must check type first
if (typeof value === 'string') {
  value.toUpperCase(); // Now it works!
}


**When to use:**
- `any`: Never! (unless migrating JavaScript to TypeScript gradually)
- `unknown`: When receiving data from external sources (API responses, user input)

**In production, I always use `unknown` because:**
1. Forces me to handle different types safely
2. Catches bugs at compile time
3. Makes code more maintainable"

4. NODE.JS EVENT LOOP
═══════════════════════════════════════════════════════════════════════════════════════

Q: Explain Node.js Event Loop.

A: "The Event Loop is how Node.js handles asynchronous operations despite being single-threaded.

**Phases of Event Loop (in order):**

1. **Timers**: Executes `setTimeout`, `setInterval` callbacks
2. **Pending Callbacks**: I/O callbacks deferred to next loop
3. **Idle, Prepare**: Internal use only
4. **Poll**: Retrieve new I/O events, execute I/O callbacks
5. **Check**: Execute `setImmediate` callbacks
6. **Close Callbacks**: Execute close event callbacks (e.g., `socket.on('close')`)

**Microtasks Queue** (executes after each phase):
- Process.nextTick (highest priority)
- Promises (.then, .catch, .finally)

**Example:**

console.log('1: Synchronous');

setTimeout(() => console.log('2: setTimeout'), 0);

setImmediate(() => console.log('3: setImmediate'));

Promise.resolve().then(() => console.log('4: Promise'));

process.nextTick(() => console.log('5: nextTick'));

console.log('6: Synchronous');

// Output:
// 1: Synchronous
// 6: Synchronous
// 5: nextTick (microtask - highest priority)
// 4: Promise (microtask)
// 2: setTimeout (timer phase)
// 3: setImmediate (check phase)


**In production, I use this knowledge to:**
- Avoid blocking the event loop with heavy computations
- Use worker threads for CPU-intensive tasks
- Properly structure async operations for optimal performance"

Q: How do you handle errors in Node.js applications?

A: "I implement multi-layered error handling:

**1. Try-Catch for Async/Await:**

async function getUser(id) {
  try {
    const user = await userRepository.findById(id);
    if (!user) {
      throw new NotFoundException(`User ${id} not found`);
    }
    return user;
  } catch (error) {
    if (error instanceof NotFoundException) {
      throw error; // Re-throw custom errors
    }
    // Log unexpected errors
    logger.error('Error fetching user:', error);
    throw new InternalServerErrorException('Failed to fetch user');
  }
}


**2. Global Error Handler (NestJS):**

@Catch()
export class GlobalExceptionFilter implements ExceptionFilter {
  catch(exception: unknown, host: ArgumentsHost) {
    const ctx = host.switchToHttp();
    const response = ctx.getResponse();

    const status = exception instanceof HttpException
      ? exception.getStatus()
      : HttpStatus.INTERNAL_SERVER_ERROR;

    const message = exception instanceof HttpException
      ? exception.message
      : 'Internal server error';

    // Log error
    logger.error(exception);

    response.status(status).json({
      statusCode: status,
      message,
      timestamp: new Date().toISOString(),
    });
  }
}


**3. Unhandled Rejection Handler:**

process.on('unhandledRejection', (reason, promise) => {
  logger.error('Unhandled Rejection at:', promise, 'reason:', reason);
  // Application should gracefully shut down
  process.exit(1);
});


**4. Custom Error Classes:**

export class NotFoundException extends Error {
  constructor(message: string) {
    super(message);
    this.name = 'NotFoundException';
  }
}


**Best Practices I follow:**
- Always log errors with context (user ID, request ID, timestamp)
- Never expose stack traces to clients in production
- Use proper HTTP status codes (404, 400, 500, etc.)
- Implement retry logic for transient failures
- Monitor error rates using tools like Sentry or New Relic"

6.1 SORTING AN ARRAY

Q: Sort an array in JavaScript.

A: "There are multiple approaches:

**1. Using Built-in Sort:**

// Ascending
const arr = [3, 1, 4, 1, 5, 9];
arr.sort((a, b) => a - b); // [1, 1, 3, 4, 5, 9]

// Descending
arr.sort((a, b) => b - a); // [9, 5, 4, 3, 1, 1]


**2. Custom Sort for Objects:**

const users = [
  { name: 'Alice', age: 30 },
  { name: 'Bob', age: 25 },
  { name: 'Charlie', age: 35 }
];

// Sort by age
users.sort((a, b) => a.age - b.age);

// Sort by name
users.sort((a, b) => a.name.localeCompare(b.name));


**Time Complexity**: O(n log n)
**Space Complexity**: O(log n) to O(n) depending on implementation"

6.2 FLATTEN THE ARRAY
═══════════════════════════════════════════════════════════════════════════════════════

Q: Flatten a nested array.

A: "I can flatten arrays in multiple ways:

**Method 1: Using flat() (ES2019):**

const nested = [1, [2, 3], [4, [5, 6]]];
const flattened = nested.flat(Infinity); // [1, 2, 3, 4, 5, 6]


**Method 2: Recursive Approach:**

function flattenArray(arr) {
  const result = [];

  for (let item of arr) {
    if (Array.isArray(item)) {
      result.push(...flattenArray(item)); // Recursive call
    } else {
      result.push(item);
    }
  }

  return result;
}

console.log(flattenArray([1, [2, [3, [4]]]])); // [1, 2, 3, 4]


**Method 3: Using reduce:**

function flattenArray(arr) {
  return arr.reduce((acc, item) => {
    return acc.concat(Array.isArray(item) ? flattenArray(item) : item);
  }, []);
}


**Time Complexity**: O(n) where n is total elements
**Space Complexity**: O(d) where d is depth (recursion stack)"

6.3 SECOND LARGEST ELEMENT
═══════════════════════════════════════════════════════════════════════════════════════

Q: Find the second largest element from an array.

A: "Optimal solution with O(n) time complexity:


function findSecondLargest(arr) {
  if (arr.length < 2) {
    return null; // Not enough elements
  }

  let largest = -Infinity;
  let secondLargest = -Infinity;

  for (let num of arr) {
    if (num > largest) {
      secondLargest = largest;
      largest = num;
    } else if (num > secondLargest && num < largest) {
      secondLargest = num;
    }
  }

  return secondLargest === -Infinity ? null : secondLargest;
}

console.log(findSecondLargest([10, 20, 25, 3, 6, 12, 52])); // 25
console.log(findSecondLargest([10, 10, 10])); // null (all same)


**Alternative (less optimal):**

function findSecondLargest(arr) {
  const unique = [...new Set(arr)].sort((a, b) => b - a);
  return unique[1] || null;
}


**Time Complexity**: O(n) - single pass
**Space Complexity**: O(1) - constant space"

6.4 TWO SUM (Return Index)
═══════════════════════════════════════════════════════════════════════════════════════

Q: Find indices of two numbers that add up to a target.

A: "Using HashMap for O(n) solution:


function twoSum(nums, target) {
  const map = new Map();

  for (let i = 0; i < nums.length; i++) {
    const complement = target - nums[i];

    if (map.has(complement)) {
      return [map.get(complement), i];
    }

    map.set(nums[i], i);
  }

  return []; // No solution found
}

console.log(twoSum([2, 7, 11, 15], 9)); // [0, 1]
console.log(twoSum([3, 2, 4], 6)); // [1, 2]


**How it works:**
1. For each number, calculate: complement = target - current_number
2. Check if complement exists in map
3. If yes, return indices
4. If no, store current number with its index

**Time Complexity**: O(n) - single pass
**Space Complexity**: O(n) - hash map storage"

7.2 DATABASE POOLING
═══════════════════════════════════════════════════════════════════════════════════════

Q: Explain database pooling and why it's important.

A: "Database pooling maintains a pool of reusable database connections
instead of creating a new connection for each request.

**Without Pooling** (Bad):

// Every request creates new connection
app.get('/users', async (req, res) => {
  const connection = await createConnection(); // Slow!
  const users = await connection.query('SELECT * FROM users');
  await connection.close();
  res.json(users);
});


**With Pooling** (Good):

// Create pool once
const pool = new Pool({
  host: 'localhost',
  database: 'mydb',
  user: 'admin',
  password: 'secret',
  max: 20, // Maximum 20 connections
  min: 5,  // Minimum 5 connections
  idleTimeoutMillis: 30000
});

app.get('/users', async (req, res) => {
  const client = await pool.connect(); // Reuses existing connection
  try {
    const result = await client.query('SELECT * FROM users');
    res.json(result.rows);
  } finally {
    client.release(); // Returns connection to pool
  }
});


**Benefits:**
1. **Performance**: Reusing connections is 10x faster than creating new ones
2. **Resource Management**: Limits max connections to database
3. **Handles Spikes**: Queue requests when pool is exhausted
4. **Connection Health**: Removes dead connections automatically

**My typical pool settings for production:**

{
  max: 20, // Max connections
  min: 5,  // Always keep 5 ready
  idleTimeoutMillis: 30000, // Close idle after 30s
  connectionTimeoutMillis: 2000, // Timeout if pool is busy
}
"

7.3 NORMALIZATION
═══════════════════════════════════════════════════════════════════════════════════════

Q: Explain database normalization.

A: "Normalization organizes data to reduce redundancy and improve integrity.

**Normal Forms:**

**1NF (First Normal Form):**
- Each column contains atomic (indivisible) values
- No repeating groups

Bad:

| ID | Name  | Phones              |
|----|-------|---------------------|
| 1  | Alice | 123-456, 789-012   |


Good:

| ID | Name  | Phone    |
|----|-------|----------|
| 1  | Alice | 123-456  |
| 1  | Alice | 789-012  |


**2NF (Second Normal Form):**
- Must be in 1NF
- All non-key attributes depend on the entire primary key

**3NF (Third Normal Form):**
- Must be in 2NF
- No transitive dependencies (non-key attributes depend only on primary key)

Bad (violates 3NF):

| OrderID | ProductID | ProductName | CategoryName |
|---------|-----------|-------------|--------------|
| 1       | 101       | Laptop      | Electronics  |

(CategoryName depends on ProductName, not OrderID)

Good (3NF):

Orders: | OrderID | ProductID |
Products: | ProductID | ProductName | CategoryID |
Categories: | CategoryID | CategoryName |


**In real projects, I:**
- Use 3NF for transactional systems (user data, orders)
- Sometimes denormalize for analytics/reporting (faster reads)
- Balance between normalization and performance"

7.4 INDEXING BEST PRACTICES
═══════════════════════════════════════════════════════════════════════════════════════

Q: How do you handle slow queries? Explain indexing.

A: "Indexing is like a book's index - helps find data quickly without scanning everything.

**Creating Indexes:**
sql
-- Single column index
CREATE INDEX idx_email ON users(email);

-- Composite index (order matters!)
CREATE INDEX idx_name_age ON users(last_name, first_name, age);

-- Unique index
CREATE UNIQUE INDEX idx_unique_email ON users(email);


**When indexes help:**
sql
-- Without index: Full table scan (slow)
SELECT * FROM users WHERE email = 'test@example.com';
-- Scans all 1 million rows

-- With index: Direct lookup (fast)
-- Uses idx_email, finds in milliseconds


**Best Practices I follow:**

**1. Index columns used in WHERE clauses:**
sql
-- Frequently filtered by status
CREATE INDEX idx_order_status ON orders(status);


**2. Index foreign keys:**
sql
CREATE INDEX idx_order_user_id ON orders(user_id);


**3. Composite index column order matters:**
sql
-- Good for: WHERE last_name = ? AND first_name = ?
-- Also good for: WHERE last_name = ?
CREATE INDEX idx_name ON users(last_name, first_name);

-- Not good for: WHERE first_name = ? (can't use index)


**4. Don't over-index:**
- Each index slows down INSERT/UPDATE/DELETE
- Indexes consume disk space
- I typically limit to 3-5 indexes per table

**Query Optimization Process:**
sql
-- 1. Identify slow query
EXPLAIN ANALYZE SELECT * FROM orders WHERE status = 'pending';

-- 2. Check if index exists
SELECT indexname FROM pg_indexes WHERE tablename = 'orders';

-- 3. Create index if needed
CREATE INDEX idx_order_status ON orders(status);

-- 4. Verify improvement
EXPLAIN ANALYZE SELECT * FROM orders WHERE status = 'pending';


**Real Example from my project:**
- Had a query taking 5 seconds on 2M rows
- Added composite index on (user_id, created_at)
- Query now takes 50ms (100x faster!)"

7.5 SECOND LARGEST SALARY (SQL)
═══════════════════════════════════════════════════════════════════════════════════════

Q: Write SQL query to find second highest salary.

A: "Multiple approaches:

**Method 1: Using LIMIT and OFFSET:**
sql
SELECT DISTINCT salary
FROM employees
ORDER BY salary DESC
LIMIT 1 OFFSET 1;


**Method 2: Using Subquery:**
sql
SELECT MAX(salary) as second_highest
FROM employees
WHERE salary < (SELECT MAX(salary) FROM employees);


**Method 3: Using ROW_NUMBER() (most flexible):**
sql
SELECT salary
FROM (
  SELECT salary,
         ROW_NUMBER() OVER (ORDER BY salary DESC) as rank
  FROM employees
) ranked
WHERE rank = 2;


**Method 4: For Nth highest:**
sql
-- Find 3rd highest salary
SELECT salary
FROM (
  SELECT DISTINCT salary,
         DENSE_RANK() OVER (ORDER BY salary DESC) as rank
  FROM employees
) ranked
WHERE rank = 3;


**Handle edge case (no second highest):**
sql
SELECT COALESCE(
  (SELECT DISTINCT salary
   FROM employees
   ORDER BY salary DESC
   LIMIT 1 OFFSET 1),
  NULL
) as second_highest_salary;


I prefer **Method 3** for production because:
- Handles ties properly with DENSE_RANK
- Easy to modify for Nth highest
- Clear and readable"

7.6 LEFT JOIN VS RIGHT JOIN
═══════════════════════════════════════════════════════════════════════════════════════

Q: Explain LEFT JOIN vs RIGHT JOIN.

A: "**LEFT JOIN**: Returns all records from left table + matching from right.
**RIGHT JOIN**: Returns all records from right table + matching from left.

**Example:**

Users:                      Orders:
| user_id | name    |      | order_id | user_id | amount |
|---------|---------|      |----------|---------|--------|
| 1       | Alice   |      | 101      | 1       | 100    |
| 2       | Bob     |      | 102      | 1       | 200    |
| 3       | Charlie |      | 103      | 3       | 150    |

LEFT JOIN:
SELECT u.name, o.amount
FROM users u
LEFT JOIN orders o ON u.user_id = o.user_id;

Result:
| name    | amount |
|---------|--------|
| Alice   | 100    |
| Alice   | 200    |
| Bob     | NULL   | ← Bob has no orders, still included
| Charlie | 150    |

RIGHT JOIN:
SELECT u.name, o.amount
FROM users u
RIGHT JOIN orders o ON u.user_id = o.user_id;

Result:
| name    | amount |
|---------|--------|
| Alice   | 100    |
| Alice   | 200    |
| Charlie | 150    |


**Real-world usage:**

sql
-- Find users who haven't placed orders
SELECT u.name
FROM users u
LEFT JOIN orders o ON u.user_id = o.user_id
WHERE o.order_id IS NULL;

-- Get all orders with user details (even if user deleted)
SELECT o.order_id, o.amount, u.name
FROM orders o
LEFT JOIN users u ON o.user_id = u.user_id;


**In practice, I mostly use LEFT JOIN** because it's more intuitive
(start with main table, add related data)."

8.1 INTERCEPTORS AND GUARDS
═══════════════════════════════════════════════════════════════════════════════════════

Q: Explain Interceptors and Guards in NestJS.

A: "**Guards** - Authentication/Authorization (executed BEFORE route handler)
**Interceptors** - Transform request/response (executed BEFORE and AFTER route handler)

**Guard Example - JWT Authentication:**

@Injectable()
export class JwtAuthGuard implements CanActivate {
  constructor(private jwtService: JwtService) {}

  canActivate(context: ExecutionContext): boolean {
    const request = context.switchToHttp().getRequest();
    const token = request.headers.authorization?.split(' ')[1];

    if (!token) {
      throw new UnauthorizedException('No token provided');
    }

    try {
      const payload = this.jwtService.verify(token);
      request.user = payload; // Attach user to request
      return true; // Allow access
    } catch (error) {
      throw new UnauthorizedException('Invalid token');
    }
  }
}

// Usage
@Controller('users')
@UseGuards(JwtAuthGuard) // Protected routes
export class UsersController {
  @Get('profile')
  getProfile(@Request() req) {
    return req.user; // Access user from guard
  }
}


**Interceptor Example - Response Transformation:**

@Injectable()
export class TransformInterceptor implements NestInterceptor {
  intercept(context: ExecutionContext, next: CallHandler): Observable<any> {

10. DESIGN PATTERNS & SOLID PRINCIPLES
═══════════════════════════════════════════════════════════════════════════════════════

Q: Explain SOLID Principles with examples.

A: "SOLID principles help write maintainable, scalable code:

**S - Single Responsibility Principle:**
Each class should have only one reason to change.

Bad:

class UserService {
  createUser(data) { /* ... */ }
  sendEmail(email) { /* ... */ } // Different responsibility!
  generateReport() { /* ... */ } // Another responsibility!
}


Good:

class UserService {
  createUser(data) { /* ... */ }
}

class EmailService {
  sendEmail(email) { /* ... */ }
}

class ReportService {
  generateReport() { /* ... */ }
}


**O - Open/Closed Principle:**
Open for extension, closed for modification.

Bad:

class PaymentProcessor {
  processPayment(type: string, amount: number) {
    if (type === 'credit_card') {
      // Process credit card
    } else if (type === 'paypal') {
      // Process PayPal
    }
    // Adding new payment method = modify this class!
  }
}


Good:

interface PaymentMethod {
  process(amount: number): void;
}

class CreditCardPayment implements PaymentMethod {
  process(amount: number) {
    // Process credit card
  }
}

class PayPalPayment implements PaymentMethod {
  process(amount: number) {
    // Process PayPal
  }
}

class PaymentProcessor {
  processPayment(method: PaymentMethod, amount: number) {
    method.process(amount); // Extensible without modification!
  }
}


**L - Liskov Substitution Principle:**
Derived classes must be substitutable for base classes.

**I - Interface Segregation Principle:**
Don't force clients to depend on interfaces they don't use.

Bad:

interface Worker {
  work(): void;
  eat(): void;
  sleep(): void;
}

class Robot implements Worker {
  work() { /* ... */ }
  eat() { /* Robots don't eat! */ }
  sleep() { /* Robots don't sleep! */ }
}


Good:

interface Workable {
  work(): void;
}

interface Eatable {
  eat(): void;
}

class Human implements Workable, Eatable {
  work() { /* ... */ }
  eat() { /* ... */ }
}

class Robot implements Workable {
  work() { /* ... */ }
}


**D - Dependency Inversion Principle:**
Depend on abstractions, not concretions.

Bad:

class UserController {
  private userService = new MySQLUserService(); // Tight coupling!
}


Good:

interface IUserService {
  getUser(id: string): Promise<User>;
}

class MySQLUserService implements IUserService {
  getUser(id: string) { /* MySQL implementation */ }
}

class MongoUserService implements IUserService {
  getUser(id: string) { /* MongoDB implementation */ }
}

class UserController {
  constructor(private userService: IUserService) {}
  // Can inject any implementation!
}


**In my projects, I use:**
- **Repository Pattern** (D principle)
- **Strategy Pattern** (O principle)
- **Factory Pattern** (O, D principles)"

12.2 FIND MISSING NUMBER FROM ARRAY
═══════════════════════════════════════════════════════════════════════════════════════

Q: Find missing number from array [1, 2, 4, 5, 6] (missing 3)

A: "Multiple approaches:

**Method 1: Using Sum Formula:**

function findMissing(arr) {
  const n = arr.length + 1; // Total numbers should be
  const expectedSum = (n * (n + 1)) / 2;
  const actualSum = arr.reduce((acc, num) => acc + num, 0);
  return expectedSum - actualSum;
}

console.log(findMissing([1, 2, 4, 5, 6])); // 3


**Method 2: Using XOR (handles duplicates):**

function findMissing(arr, n) {
  let xor = 0;

  // XOR all array elements
  for (let num of arr) {
    xor ^= num;
  }

  // XOR all numbers from 1 to n
  for (let i = 1; i <= n; i++) {
    xor ^= i;
  }

  return xor; // Missing number
}


**Time Complexity**: O(n)
**Space Complexity**: O(1)"

12.3 QUOTIENT WITHOUT DIVISION OPERATOR
═══════════════════════════════════════════════════════════════════════════════════════

Q: Find quotient of a=5, b=2 without using / operator (output should be 2)

A:

function findQuotient(a, b) {
  if (b === 0) {
    throw new Error('Division by zero');
  }

  let quotient = 0;
  let sign = (a < 0) ^ (b < 0) ? -1 : 1; // Handle negative numbers

  a = Math.abs(a);
  b = Math.abs(b);

  while (a >= b) {
    a -= b;
    quotient++;
  }

  return quotient * sign;
}

console.log(findQuotient(5, 2)); // 2
console.log(findQuotient(10, 3)); // 3
console.log(findQuotient(-10, 3)); // -3


**Optimized (using bit shifting):**

function findQuotient(dividend, divisor) {
  if (divisor === 0) throw new Error('Division by zero');

  let sign = (dividend < 0) ^ (divisor < 0) ? -1 : 1;
  dividend = Math.abs(dividend);
  divisor = Math.abs(divisor);

  let quotient = 0;
  while (dividend >= divisor) {
    let temp = divisor;
    let multiple = 1;

    while (dividend >= (temp << 1)) {
      temp <<= 1;
      multiple <<= 1;
    }

    dividend -= temp;
    quotient += multiple;
  }

  return quotient * sign;
}
"

14.1 READING LARGE DATASETS WITH STREAMS

Q: How do you read large CSV files and insert into database?

A: "I use streams to avoid loading entire file into memory:


import { createReadStream } from 'fs';
import { parse } from 'csv-parse';
import { Injectable } from '@nestjs/common';

@Injectable()
export class CsvImportService {
  async importUsers(filePath: string) {
    return new Promise((resolve, reject) => {
      const results = [];
      let batch = [];
      const BATCH_SIZE = 1000;

      createReadStream(filePath)
        .pipe(parse({ columns: true, skip_empty_lines: true }))
        .on('data', async (row) => {
          batch.push({
            name: row.name,
            email: row.email,
            age: parseInt(row.age)
          });

          // Insert in batches for efficiency
          if (batch.length >= BATCH_SIZE) {
            this.pause(); // Pause stream
            await this.userRepository.insert(batch);
            batch = [];
            this.resume(); // Resume stream
          }
        })
        .on('end', async () => {
          // Insert remaining records
          if (batch.length > 0) {
            await this.userRepository.insert(batch);
          }
          resolve(`Imported ${results.length} records`);
        })
        .on('error', (error) => {
          reject(error);
        });
    });
  }
}


**Benefits:**
- Memory-efficient (10GB file uses only ~100MB RAM)
- Fast (batch inserts vs individual)
- Handles errors gracefully

**Production example:**
- Imported 5 million user records (2GB CSV)
- Used 150MB memory
- Completed in 10 minutes vs 2 hours with traditional approach"

15.1 BIRTHDAY WISHES AT MIDNIGHT IN USER'S TIMEZONE

Q: "How would you send birthday wishes at exactly 12:00 AM in each user's timezone?"

A: "This is a complex distributed scheduling problem. Here's my approach:

**Solution Architecture:**


// 1. Store user's timezone in database
interface User {
  id: string;
  name: string;
  birthday: Date; // Only month and day matter
  timezone: string; // 'Asia/Kolkata', 'America/New_York', etc.
}

// 2. Cron job runs every hour checking for birthdays
@Cron('0 * * * *') // Every hour
async checkBirthdaysThisHour() {
  const now = new Date();
  const currentHour = now.getUTCHours();

  // Find all timezones where it's currently midnight (00:00)
  const targetTimezones = this.getTimezonesAtMidnight(currentHour);

  // Get users whose birthday is today AND in those timezones
  const users = await this.userRepository.find({
    where: {
      timezone: In(targetTimezones),
      birthday: Raw(alias => `EXTRACT(MONTH FROM ${alias}) = ${now.getMonth() + 1}
                              AND EXTRACT(DAY FROM ${alias}) = ${now.getDate()}`)
    }
  });

  // Send birthday wishes
  for (const user of users) {
    await this.sendBirthdayWish(user);
  }
}

// 3. Helper to find timezones at midnight
getTimezonesAtMidnight(currentUTCHour: number): string[] {
  // Map UTC hours to timezones at midnight
  const timezoneMap = {
    0: ['UTC', 'GMT'],
    5: ['Asia/Kolkata'], // UTC+5:30 → midnight at 18:30 UTC
    7: ['Asia/Bangkok'], // UTC+7
    8: ['Asia/Singapore'],
    // ... map all timezones
  };

  return timezoneMap[currentUTCHour] || [];
}

// 4. Send birthday notification
async sendBirthdayWish(user: User) {
  // Add to queue for reliability
  await this.queue.add('send-birthday-wish', {
    userId: user.id,
    name: user.name,
    timezone: user.timezone
  });
}

// 5. Queue processor
@Process('send-birthday-wish')
async processBirthdayWish(job: Job) {
  const { userId, name } = job.data;

  try {
    // Send email
    await this.emailService.send({
      to: user.email,
      subject: `Happy Birthday ${name}!`,
      template: 'birthday'
    });

    // Send push notification
    await this.pushService.send(userId, {
      title: 'Happy Birthday!',
      body: `Wishing you an amazing day, ${name}!`
    });

    // Log success
    await this.logService.log({
      userId,
      event: 'birthday_wish_sent',
      timestamp: new Date()
    });
  } catch (error) {
    // Retry on failure
    throw error;
  }
}


**Alternative: More Precise Approach**


// Schedule individual jobs for each user
@Cron('0 0 * * *') // Run at midnight UTC
async scheduleBirthdayWishes() {
  const today = new Date();

  // Get all users whose birthday is today
  const users = await this.userRepository.find({
    where: {
      birthday: Raw(alias => `EXTRACT(MONTH FROM ${alias}) = ${today.getMonth() + 1}
                              AND EXTRACT(DAY FROM ${alias}) = ${today.getDate()}`)
    }
  });

  for (const user of users) {
    // Calculate when midnight occurs in user's timezone
    const userMidnight = this.getMidnightInUserTimezone(user.timezone);

    // Schedule job at that specific time
    await this.scheduler.schedule(userMidnight, 'send-birthday-wish', {
      userId: user.id
    });
  }
}

getMidnightInUserTimezone(timezone: string): Date {
  const now = new Date();
  const userTime = new Date(now.toLocaleString('en-US', { timeZone: timezone }));

  // Set to midnight in user's timezone
  userTime.setHours(0, 0, 0, 0);

  // If midnight already passed today, schedule for tomorrow
  if (userTime < now) {
    userTime.setDate(userTime.getDate() + 1);
  }

  return userTime;
}


**Tech Stack:**
- **PostgreSQL**: Store users with timezone
- **Bull/BullMQ**: Job queue for reliability
- **Node-Cron**: Scheduled tasks
- **Moment-Timezone**: Timezone handling

**Considerations:**
- Handle users changing timezones
- Prevent duplicate sends (idempotency key)
- Handle failures with retries
- Monitor success rate

**Scaling:**
- Use distributed cron (one instance runs job)
- Redis lock to prevent duplicate processing
- Partition users by timezone for parallel processing"
