PART 1: WHAT IS CI/CD? (Real-World Analogy)
═══════════════════════════════════════════════════════════════════════════════════════

Think of CI/CD as an AUTOMATED FACTORY for software:

Traditional Way (Manual Deployment):
┌─────────────────────────────────────────────────────┐
│  Developer writes code                              │
│  ↓                                                  │
│  Manually run tests (takes 30 minutes)             │
│  ↓                                                  │
│  Manually build application (takes 15 minutes)     │
│  ↓                                                  │
│  Email DevOps team to deploy                       │
│  ↓                                                  │
│  Wait 2 days for deployment approval               │
│  ↓                                                  │
│  Manual deployment (often breaks!)                 │
│  ↓                                                  │
│  "It worked on my machine!" 😫                      │
│                                                     │
│  TOTAL TIME: 2-3 days per deployment               │
└─────────────────────────────────────────────────────┘

With CI/CD (Automated):
┌─────────────────────────────────────────────────────┐
│  Developer pushes code to Git                       │
│  ↓                                                  │
│  ✅ Automatically run tests (5 minutes)            │
│  ↓                                                  │
│  ✅ Automatically build Docker image (3 minutes)   │
│  ↓                                                  │
│  ✅ Automatically deploy to staging (2 minutes)    │
│  ↓                                                  │
│  ✅ Run smoke tests (2 minutes)                    │
│  ↓                                                  │
│  ✅ Deploy to production (5 minutes)               │
│  ↓                                                  │
│  DONE! 🎉                                          │
│                                                     │
│  TOTAL TIME: 17 minutes!                           │
└─────────────────────────────────────────────────────┘

REAL-WORLD EXAMPLE: Pizza Delivery

WITHOUT CI/CD:
You order pizza → Chef makes it → Someone checks it → Another person boxes it
→ Another person delivers it → Takes 2 hours! 🍕

WITH CI/CD:
You order pizza → Automated assembly line makes it → Quality checked automatically
→ Auto-packed → Auto-dispatched → Delivered in 30 minutes! 🚀

CI/CD = Continuous Integration / Continuous Deployment
"Continuous" = Automated and frequent (not manual and rare)

PART 2: CI (CONTINUOUS INTEGRATION) - The "Quality Control"
═══════════════════════════════════════════════════════════════════════════════════════

WHAT IS CI?
"Automatically test and integrate code changes frequently"

PROBLEM WITHOUT CI:
┌──────────────────────────────────────────────┐
│  Developer A works on Feature X (2 weeks)   │
│  Developer B works on Feature Y (2 weeks)   │
│                                              │
│  Week 3: Try to merge...                    │
│  💥 MERGE CONFLICTS EVERYWHERE!             │
│  💥 Tests fail!                             │
│  💥 Code doesn't compile!                   │
│                                              │
│  Takes 3 days to fix! 😭                    │
└──────────────────────────────────────────────┘

WITH CI (Continuous Integration):
┌──────────────────────────────────────────────┐
│  Developer A: Push code → Auto test ✅       │
│  Developer B: Push code → Auto test ✅       │
│  Developer A: Push again → Auto test ✅      │
│  Developer B: Push again → Auto test ✅      │
│                                              │
│  Conflicts detected EARLY (same day!)        │
│  Fix takes 10 minutes! 🎉                   │
└──────────────────────────────────────────────┘

CI WORKFLOW (Step by Step):

Step 1: Developer pushes code to Git
┌──────────────┐
│  Developer   │ git push origin main
└──────┬───────┘
       │
       ▼
┌──────────────┐
│  GitHub      │ Code stored in repository
└──────┬───────┘
       │ Triggers CI pipeline
       ▼

Step 2: CI Server runs automatically
┌─────────────────────────────────────────┐
│        CI Server (GitHub Actions)       │
│                                         │
│  1. ✅ Checkout code                    │
│  2. ✅ Install dependencies             │
│  3. ✅ Run linter (code quality)        │
│  4. ✅ Run unit tests (100 tests)       │
│  5. ✅ Run integration tests            │
│  6. ✅ Check code coverage (>80%)       │
│  7. ✅ Build application                │
│  8. ✅ Create artifacts                 │
└────────┬────────────────────────────────┘
         │
         ▼
┌─────────────────┐
│   All Passed!   │ Ready for deployment ✅
└─────────────────┘

If ANY step fails:
┌─────────────────────────────────────────┐
│  ❌ Tests failed!                       │
│  ❌ Deployment BLOCKED                  │
│  ❌ Email sent to developer             │
│  ❌ Slack notification                  │
│                                         │
│  Developer must fix before merging!     │
└─────────────────────────────────────────┘

CI BENEFITS:
✅ Find bugs early (minutes, not days)
✅ Faster feedback (know immediately if code breaks)
✅ Higher quality (tests run on every commit)
✅ Less integration problems
✅ More confident deployments

PART 3: CD (CONTINUOUS DEPLOYMENT) - The "Delivery System"
═══════════════════════════════════════════════════════════════════════════════════════

TWO MEANINGS OF CD:

1. CONTINUOUS DELIVERY (Semi-Automated)
   Code is READY to deploy, but requires manual approval

2. CONTINUOUS DEPLOYMENT (Fully Automated)
   Code is AUTOMATICALLY deployed to production (no manual step)

CONTINUOUS DELIVERY:
┌──────────────┐
│  Code Pass   │ All tests passed
│   CI Tests   │
└──────┬───────┘
       │ Automatic
       ▼
┌──────────────┐
│  Deploy to   │ Staging environment
│   Staging    │
└──────┬───────┘
       │ Manual button click
       ▼
┌──────────────┐
│  Deploy to   │ Production environment
│  Production  │
└──────────────┘

CONTINUOUS DEPLOYMENT (More Advanced):
┌──────────────┐
│  Code Pass   │ All tests passed
│   CI Tests   │
└──────┬───────┘
       │ Automatic
       ▼
┌──────────────┐
│  Deploy to   │ Staging environment
│   Staging    │
└──────┬───────┘
       │ Automatic (if tests pass)
       ▼
┌──────────────┐
│  Deploy to   │ Production environment (NO manual approval!)
│  Production  │
└──────────────┘

CD WORKFLOW (Step by Step):

Step 1: CI Completes Successfully
┌──────────────┐
│  CI Passed   │ ✅ All tests green
└──────┬───────┘
       │
       ▼

Step 2: Build Docker Image
┌─────────────────────────────────────────┐
│  Build Docker Image                     │
│                                         │
│  FROM node:16-alpine                    │
│  COPY . /app                            │
│  RUN npm install                        │
│  CMD ["npm", "start"]                   │
│                                         │
│  Image: myapp:v1.2.3                    │
└────────┬────────────────────────────────┘
         │
         ▼

Step 3: Push to Container Registry
┌─────────────────────────────────────────┐
│  Docker Registry (Docker Hub/ECR)       │
│                                         │
│  myapp:v1.2.3 (uploaded)                │
└────────┬────────────────────────────────┘
         │
         ▼

Step 4: Deploy to Staging
┌─────────────────────────────────────────┐
│  Staging Environment (Kubernetes)       │
│                                         │
│  kubectl set image deployment/myapp     │
│    myapp=myapp:v1.2.3                   │
│                                         │
│  Status: Running ✅                     │
└────────┬────────────────────────────────┘
         │
         ▼

Step 5: Run Smoke Tests
┌─────────────────────────────────────────┐
│  Smoke Tests (Quick checks)             │
│                                         │
│  ✅ App is running                      │
│  ✅ Health endpoint responds            │
│  ✅ Database connection works           │
│  ✅ API endpoints work                  │
└────────┬────────────────────────────────┘
         │ If all pass
         ▼

Step 6: Deploy to Production
┌─────────────────────────────────────────┐
│  Production Environment (Kubernetes)    │
│                                         │
│  Rolling update (zero downtime):        │
│  - Start new pods with v1.2.3           │
│  - Gradual traffic shift               │
│  - Terminate old pods                   │
│                                         │
│  Status: Deployed ✅                    │
└─────────────────────────────────────────┘

PART 5: DEPLOYMENT STRATEGIES (How to Deploy Safely)
═══════════════════════════════════════════════════════════════════════════════════════

1. ROLLING DEPLOYMENT ⭐ MOST COMMON

How it works: Replace instances gradually

┌────────────────────────────────────────────┐
│  STEP 1: Current State (v1.0)              │
│  ┌────┐ ┌────┐ ┌────┐ ┌────┐               │
│  │ v1 │ │ v1 │ │ v1 │ │ v1 │ ← 100% traffic │
│  └────┘ └────┘ └────┘ └────┘               │
└────────────────────────────────────────────┘

┌────────────────────────────────────────────┐
│  STEP 2: Deploy 1 new instance (v2.0)      │
│  ┌────┐ ┌────┐ ┌────┐ ┌────┐               │
│  │ v1 │ │ v1 │ │ v1 │ │ v2 │ ← Some traffic │
│  └────┘ └────┘ └────┘ └────┘               │
└────────────────────────────────────────────┘

┌────────────────────────────────────────────┐
│  STEP 3: Remove 1 old instance             │
│  ┌────┐ ┌────┐ ┌────┐                      │
│  │ v1 │ │ v1 │ │ v2 │                      │
│  └────┘ └────┘ └────┘                      │
└────────────────────────────────────────────┘

┌────────────────────────────────────────────┐
│  STEP 4: Continue until all replaced       │
│  ┌────┐ ┌────┐ ┌────┐ ┌────┐               │
│  │ v2 │ │ v2 │ │ v2 │ │ v2 │ ← 100% traffic │
│  └────┘ └────┘ └────┘ └────┘               │
└────────────────────────────────────────────┘

PROS:
✅ Zero downtime
✅ Gradual rollout
✅ Can rollback quickly

CONS:
❌ Both versions run simultaneously
❌ Need backward compatibility

2. BLUE-GREEN DEPLOYMENT

How it works: Two identical environments, switch instantly

┌────────────────────────────────────────────┐
│  STEP 1: Blue is LIVE, Green is preparing  │
│                                            │
│  BLUE (v1.0) ◄────── 100% traffic         │
│  ┌────┐ ┌────┐ ┌────┐                     │
│  │ v1 │ │ v1 │ │ v1 │                     │
│  └────┘ └────┘ └────┘                     │
│                                            │
│  GREEN (v2.0)       (0% traffic)          │
│  ┌────┐ ┌────┐ ┌────┐                     │
│  │ v2 │ │ v2 │ │ v2 │                     │
│  └────┘ └────┘ └────┘                     │
└────────────────────────────────────────────┘

┌────────────────────────────────────────────┐
│  STEP 2: Test Green environment            │
│                                            │
│  BLUE (v1.0) ◄────── 100% traffic         │
│  ┌────┐ ┌────┐ ┌────┐                     │
│  │ v1 │ │ v1 │ │ v1 │                     │
│  └────┘ └────┘ └────┘                     │
│                                            │
│  GREEN (v2.0) ◄──── Internal testing      │
│  ┌────┐ ┌────┐ ┌────┐                     │
│  │ v2 │ │ v2 │ │ v2 │ ✅ Tests pass       │
│  └────┘ └────┘ └────┘                     │
└────────────────────────────────────────────┘

┌────────────────────────────────────────────┐
│  STEP 3: SWITCH! (Instant)                 │
│                                            │
│  BLUE (v1.0)        (0% traffic)          │
│  ┌────┐ ┌────┐ ┌────┐                     │
│  │ v1 │ │ v1 │ │ v1 │                     │
│  └────┘ └────┘ └────┘                     │
│                                            │
│  GREEN (v2.0) ◄────── 100% traffic        │
│  ┌────┐ ┌────┐ ┌────┐                     │
│  │ v2 │ │ v2 │ │ v2 │                     │
│  └────┘ └────┘ └────┘                     │
└────────────────────────────────────────────┘

PROS:
✅ Instant switch (no gradual rollout)
✅ Easy rollback (switch back to Blue)
✅ Full testing before switch

CONS:
❌ Need 2x resources
❌ Expensive

3. CANARY DEPLOYMENT

How it works: Test with small % of users first

┌────────────────────────────────────────────┐
│  STEP 1: Deploy to 5% of users             │
│                                            │
│  STABLE (v1.0) ◄────── 95% traffic        │
│  ┌────┐ ┌────┐ ┌────┐ ┌────┐ ┌────┐       │
│  │ v1 │ │ v1 │ │ v1 │ │ v1 │ │ v1 │       │
│  └────┘ └────┘ └────┘ └────┘ └────┘       │
│                                            │
│  CANARY (v2.0) ◄────── 5% traffic         │
│  ┌────┐                                    │
│  │ v2 │ 🐤 Test with few users             │
│  └────┘                                    │
└────────────────────────────────────────────┘

┌────────────────────────────────────────────┐
│  STEP 2: If OK, increase to 50%            │
│                                            │
│  STABLE (v1.0) ◄────── 50% traffic        │
│  ┌────┐ ┌────┐ ┌────┐                     │
│  │ v1 │ │ v1 │ │ v1 │                     │
│  └────┘ └────┘ └────┘                     │
│                                            │
│  CANARY (v2.0) ◄────── 50% traffic        │
│  ┌────┐ ┌────┐ ┌────┐                     │
│  │ v2 │ │ v2 │ │ v2 │ ✅ Metrics good     │
│  └────┘ └────┘ └────┘                     │
└────────────────────────────────────────────┘

┌────────────────────────────────────────────┐
│  STEP 3: If OK, roll out to 100%           │
│                                            │
│  CANARY (v2.0) ◄────── 100% traffic       │
│  ┌────┐ ┌────┐ ┌────┐ ┌────┐ ┌────┐ ┌────┐│
│  │ v2 │ │ v2 │ │ v2 │ │ v2 │ │ v2 │ │ v2 ││
│  └────┘ └────┘ └────┘ └────┘ └────┘ └────┘│
│                                            │
│  STABLE (v1.0) - Deleted                   │
└────────────────────────────────────────────┘

PROS:
✅ Low risk (test with few users first)

  CMD node -e "require('http').get('http://localhost:3000/health')"

WHY KUBERNETES FOR DEPLOYMENT?

WITHOUT KUBERNETES:
- Manually start containers on servers
- Manually restart if they crash
- Manually distribute traffic
- Manually scale up/down
= NIGHTMARE! 😫

WITH KUBERNETES:
- Automatically manages containers
- Automatically restarts crashed containers
- Automatically distributes traffic
- Automatically scales based on load
= AUTOMATED! 🎉

KUBERNETES DEPLOYMENT YAML:

# deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
  labels:
    app: myapp
spec:
  replicas: 3  # Run 3 instances

  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1        # At most 1 extra pod during update
      maxUnavailable: 0  # Zero downtime

  selector:
    matchLabels:
      app: myapp

  template:
    metadata:
      labels:
        app: myapp
    spec:
      containers:
      - name: myapp
        image: mycompany/myapp:v1.2.3

        ports:
        - containerPort: 3000

        # Resource limits
        resources:
          requests:
            cpu: "100m"
            memory: "128Mi"
          limits:
            cpu: "500m"
            memory: "512Mi"

        # Health checks
        livenessProbe:
          httpGet:
            path: /health
            port: 3000
          initialDelaySeconds: 30
          periodSeconds: 10

        readinessProbe:
          httpGet:
            path: /ready
            port: 3000
          initialDelaySeconds: 5
          periodSeconds: 5

        # Environment variables from ConfigMap
        envFrom:
        - configMapRef:
            name: myapp-config

        # Secrets
        env:
        - name: DB_PASSWORD
          valueFrom:
            secretKeyRef:
              name: myapp-secrets
              key: db-password

---
# service.yaml
apiVersion: v1
kind: Service
metadata:
  name: myapp
spec:
  selector:
    app: myapp
  ports:
  - port: 80
    targetPort: 3000
  type: LoadBalancer

CI/CD WITH KUBERNETES:

GitHub Actions → Build Docker → Push to Registry → Deploy to K8s

.github/workflows/deploy.yml:

```yaml
name: Deploy to Kubernetes

on:
  push:
    branches: [main]

env:
  IMAGE_NAME: mycompany/myapp
  VERSION: ${{ github.sha }}

jobs:
  deploy:
    runs-on: ubuntu-latest

    steps:
      # Checkout code
      - uses: actions/checkout@v3

      # Setup Docker Buildx
      - name: Set up Docker Buildx
        uses: docker/setup-buildx-action@v2

      # Login to Docker Hub
      - name: Login to Docker Hub
        uses: docker/login-action@v2
        with:
          username: ${{ secrets.DOCKER_USERNAME }}
          password: ${{ secrets.DOCKER_PASSWORD }}

      # Build and push Docker image
      - name: Build and push
        uses: docker/build-push-action@v4
        with:
          context: .
          push: true
          tags: |
            ${{ env.IMAGE_NAME }}:${{ env.VERSION }}
            ${{ env.IMAGE_NAME }}:latest
          cache-from: type=registry,ref=${{ env.IMAGE_NAME }}:latest
          cache-to: type=inline

      # Setup kubectl
      - name: Setup kubectl
        uses: azure/setup-kubectl@v3

      # Configure kubectl
      - name: Configure kubectl
        run: |
          echo "${{ secrets.KUBE_CONFIG }}" | base64 -d > kubeconfig
          export KUBECONFIG=kubeconfig

      # Update deployment
      - name: Deploy to Kubernetes
        run: |
          kubectl set image deployment/myapp \
            myapp=${{ env.IMAGE_NAME }}:${{ env.VERSION }} \
            --record

          # Wait for rollout to complete
          kubectl rollout status deployment/myapp

          # Verify deployment
          kubectl get pods -l app=myapp

      # Rollback if deployment fails
      - name: Rollback on failure
        if: failure()
        run: |
          kubectl rollout undo deployment/myapp
```

PART 10: COMMON INTERVIEW QUESTIONS & ANSWERS
═══════════════════════════════════════════════════════════════════════════════════════

Q1: What is CI/CD and why is it important?

A: "CI/CD stands for Continuous Integration and Continuous Deployment.
    It automates the software delivery process from code commit to production."

Benefits:
✅ Faster deployments (minutes vs days)
✅ Higher quality (automated testing)
✅ Early bug detection (test on every commit)
✅ Reduced risk (small, frequent changes)
✅ Better collaboration (immediate feedback)

Q2: What's the difference between Continuous Delivery and Continuous Deployment?

A: "Continuous Delivery requires manual approval for production deployment,
    Continuous Deployment is fully automated to production."

Continuous Delivery:
Code → CI → Build → Deploy to Staging → [Manual Approval] → Production

Continuous Deployment:
Code → CI → Build → Deploy to Staging → [Automatic] → Production

Use Delivery when:
- Need compliance approvals
- Want manual control
- High-risk changes

Use Deployment when:
- Full automation desired
- Fast feedback needed
- Low-risk changes

Q3: How do you handle database migrations in CI/CD?

A: "Use versioned migration scripts that run automatically before deployment"

Strategy:
1. Write migration scripts (numbered: 001_add_users_table.sql)
2. Run migrations before application deployment
3. Make migrations backward compatible
4. Test migrations in staging first
5. Keep rollback scripts ready

Example Flow:
```bash
# In CI/CD pipeline
- run: npm run migrate:up      # Apply migrations
- run: npm run test             # Test with new schema
- run: kubectl apply -f k8s/    # Deploy new code
```

Backward Compatible Example:
```sql
-- Good: Add column with default value
ALTER TABLE users ADD COLUMN phone VARCHAR(20) DEFAULT '';

-- Bad: Drop column immediately
-- ALTER TABLE users DROP COLUMN email; ❌
```

Q4: What deployment strategy would you use for a critical payment service?

A: "Blue-Green or Canary deployment with extensive monitoring"

Reasoning:
- Zero downtime required (payments can't fail)
- Need instant rollback capability
- Test with small % of traffic first (Canary)
- Monitor error rates closely
- Keep old version ready (Blue-Green)

Implementation:
1. Deploy new version alongside old (Blue-Green)
2. Route 5% traffic to new version (Canary)
3. Monitor: error rate, response time, success rate
4. If metrics good: gradually increase to 100%
5. If metrics bad: instant switch back to old version

Q5: How do you secure secrets in CI/CD pipelines?

A: "Use dedicated secret management tools, never commit secrets to Git"

Best Practices:
✅ Use GitHub Secrets / GitLab CI Variables
✅ Use HashiCorp Vault / AWS Secrets Manager
✅ Rotate secrets regularly
✅ Encrypt secrets at rest
✅ Use RBAC (Role-Based Access Control)
✅ Audit secret access

Example (GitHub Actions):
```yaml
- name: Deploy
  env:
    DB_PASSWORD: ${{ secrets.DB_PASSWORD }}
    API_KEY: ${{ secrets.API_KEY }}
  run: ./deploy.sh
```

Never do:
❌ Commit .env files
❌ Hardcode passwords in code
❌ Print secrets in logs
❌ Store secrets in Dockerfiles

Q6: What metrics do you monitor after deployment?

A: "Golden Signals: Latency, Traffic, Errors, Saturation"

1. Latency (Response Time)
   - p50, p95, p99 response times
   - Target: < 200ms (p95)

2. Traffic (Request Rate)
   - Requests per second
   - Compare before/after deployment

3. Errors (Error Rate)
   - 5xx errors, 4xx errors
   - Target: < 0.1%

4. Saturation (Resource Usage)
   - CPU, memory, disk, network
   - Target: < 80%

5. Business Metrics
   - Conversion rate
   - User sign-ups
   - Transactions processed

Q7: How do you handle a failed deployment?

A: "Immediate rollback, investigate, fix, and redeploy"

Incident Response:
1. Detect issue (monitoring alerts)
2. Immediate rollback (kubectl rollout undo)
3. Notify team (Slack/PagerDuty)
4. Investigate root cause
5. Fix in development
6. Test thoroughly
7. Redeploy with confidence

Post-Incident:
- Write post-mortem
- Update runbooks
- Improve monitoring
- Add tests to prevent recurrence

Q8: What testing strategies do you use in CI/CD?

A: "Test pyramid: Unit tests (70%), Integration tests (20%), E2E tests (10%)"

┌─────────────────────────────────────────┐
│                                         │
│         ▲                               │
│        / \  E2E Tests (10%)             │
│       /___\  - Slow, expensive          │
│      /     \  - User flows              │
│     /       \                           │
│    /_________\  Integration (20%)       │
│   /           \  - API tests            │
│  /             \  - DB tests            │
│ /_______________\  Unit (70%)           │
│                    - Fast, cheap        │
│                    - Functions/classes  │
└─────────────────────────────────────────┘

In CI/CD Pipeline:
1. Unit tests: Every commit (2-5 minutes)
2. Integration tests: Every commit (5-10 minutes)
3. E2E tests: Before production (10-20 minutes)
4. Smoke tests: After deployment (2-3 minutes)
5. Performance tests: Nightly (30-60 minutes)

Q9: How do you achieve zero-downtime deployments?

A: "Rolling updates with health checks and readiness probes"

Key Techniques:
1. Rolling Updates
   - Update pods gradually
   - Always keep some old pods running

2. Health Checks
   - Liveness: Is container alive?
   - Readiness: Is container ready for traffic?

3. Load Balancer
   - Routes traffic only to ready pods
   - Removes unhealthy pods automatically

4. Graceful Shutdown
   - Wait for in-flight requests to complete
   - Stop accepting new requests first

5. Database Migrations
   - Make schema changes backward compatible
   - Deploy schema changes separately from code

Q10: What's the difference between Docker and Kubernetes in CI/CD?

A: "Docker packages the application, Kubernetes deploys and manages it"

┌──────────────────┬─────────────────┬──────────────────┐
│   Aspect         │    Docker       │   Kubernetes     │
├──────────────────┼─────────────────┼──────────────────┤
│ Purpose          │ Containerize    │ Orchestrate      │
│ Scope            │ Single host     │ Multiple hosts   │
│ Scaling          │ Manual          │ Automatic        │
│ Load Balancing   │ No              │ Yes              │
│ Self-Healing     │ No              │ Yes              │
│ Rollout          │ Manual          │ Automated        │
└──────────────────┴─────────────────┴──────────────────┘

In CI/CD:
1. Docker: Build and package application
2. Kubernetes: Deploy and manage containers

Together:
CI → Build Docker image → Push to registry → K8s deploys it

PART 11: BEST PRACTICES FOR CI/CD
═══════════════════════════════════════════════════════════════════════════════════════

1. COMMIT EARLY, COMMIT OFTEN ⭐
   - Push code multiple times a day
   - Small commits = easier to debug
   - Don't wait until feature is "perfect"

2. AUTOMATE EVERYTHING
   - Tests
   - Builds
   - Deployments
   - Monitoring
   - Rollbacks

3. FAIL FAST
   - Run quick tests first (unit tests)
   - Run slow tests later (E2E tests)
   - Stop pipeline on first failure

4. KEEP BUILDS FAST
   - Target: < 10 minutes
   - Use caching
   - Parallelize tests
   - Optimize Docker builds

5. TEST IN PRODUCTION-LIKE ENVIRONMENT
   - Staging should mirror production
   - Same OS, same versions
   - Use Docker for consistency

6. MONITOR EVERYTHING
   - Application metrics
   - Infrastructure metrics
   - Business metrics
   - User experience

7. MAKE ROLLBACKS EASY
   - Keep previous versions
   - Automate rollback process
   - Test rollback regularly

8. USE FEATURE FLAGS
   - Deploy code with features disabled
   - Enable features gradually
   - Instant rollback (just toggle flag)

9. SECURITY IN PIPELINE
   - Scan dependencies (Snyk)
   - Scan containers (Trivy)
   - Scan code (SonarQube)
   - Check secrets (git-secrets)

10. DOCUMENT YOUR PIPELINE
    - README with pipeline overview
    - Runbooks for common issues
    - Architecture diagrams
    - Incident response procedures
