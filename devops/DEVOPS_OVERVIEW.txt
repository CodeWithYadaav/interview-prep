WHAT IS DEVOPS? (The Big Picture)
═══════════════════════════════════════════════════════════════════════════════════════

DevOps = Development + Operations

TRADITIONAL APPROACH (Waterfall):
┌────────────────────────────────────────────────────────────────┐
│  Developers write code (3 months)                              │
│  ↓                                                             │
│  Throw code "over the wall" to Operations team                 │
│  ↓                                                             │
│  Operations team tries to deploy (2 weeks)                     │
│  ↓                                                             │
│  Doesn't work! Blame game begins! 😫                           │
│  ↓                                                             │
│  Back to developers (1 month to fix)                           │
│  ↓                                                             │
│  Total time: 4-5 months per release                            │
└────────────────────────────────────────────────────────────────┘

DEVOPS APPROACH (Agile):
┌────────────────────────────────────────────────────────────────┐
│  Developers & Operations work together                         │
│  ↓                                                             │
│  Automate everything (CI/CD pipelines)                         │
│  ↓                                                             │
│  Deploy multiple times per day                                 │
│  ↓                                                             │
│  Monitor, learn, improve continuously                          │
│  ↓                                                             │
│  Total time: Minutes per release! 🚀                           │
└────────────────────────────────────────────────────────────────┘

DEVOPS = Culture + Tools + Practices

═══════════════════════════════════════════════════════════════════════════════════════
DOCKER - "The Shipping Container for Code"
═══════════════════════════════════════════════════════════════════════════════════════

WHAT IT DOES:
Packages your application with all dependencies into a container

PROBLEM IT SOLVES:
"Works on my machine" syndrome

ANALOGY:
Before containers: Shipping loose cargo (different sizes, hard to handle)
With containers: Shipping standard containers (same size, easy to handle)

REAL-WORLD USE:
```dockerfile
# Dockerfile
FROM node:16-alpine                 # Base image
WORKDIR /app                        # Set directory
COPY package*.json ./               # Copy dependencies
RUN npm install                     # Install
COPY . .                            # Copy code
CMD ["npm", "start"]                # Run app
```

Build & Run:
```bash
docker build -t myapp .             # Build image
docker run -p 3000:3000 myapp       # Run container
```

KEY CONCEPTS:
- Image: Blueprint (recipe)
- Container: Running instance (actual cake)
- Registry: Storage (Docker Hub)
- Volume: Persistent data

WHEN TO USE:
✅ Microservices
✅ Development environments
✅ Cloud deployments
✅ CI/CD pipelines

═══════════════════════════════════════════════════════════════════════════════════════
KUBERNETES - "The Orchestra Conductor for Containers"
═══════════════════════════════════════════════════════════════════════════════════════

WHAT IT DOES:
Automates deployment, scaling, and management of containerized applications

PROBLEM IT SOLVES:
Managing hundreds of containers manually is impossible

ANALOGY:
Without K8s: You manually start/stop 100 musicians, fix broken instruments
With K8s: Conductor automatically manages everything

REAL-WORLD USE:
```yaml
# deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
spec:
  replicas: 3                       # Run 3 copies
  template:
    spec:
      containers:
      - name: myapp
        image: myapp:v1.0.0
        ports:
        - containerPort: 3000
```

Deploy:
```bash
kubectl apply -f deployment.yaml    # Deploy
kubectl scale deployment myapp --replicas=10  # Scale
kubectl rollout undo deployment myapp         # Rollback
```

KEY CONCEPTS:
- Pod: Smallest unit (1+ containers)
- Deployment: Manages pods
- Service: Stable network endpoint
- Namespace: Environment isolation

WHEN TO USE:
✅ Microservices at scale
✅ Need auto-scaling
✅ High availability required
✅ 10+ containers

═══════════════════════════════════════════════════════════════════════════════════════
REDIS - "The Super Fast Memory for Your Application"
═══════════════════════════════════════════════════════════════════════════════════════

WHAT IT DOES:
In-memory data store (extremely fast cache)

PROBLEM IT SOLVES:
Database queries are slow (50ms), Redis is 50x faster (1ms)

ANALOGY:
Database: Filing cabinet (slow to access)
Redis: Sticky notes on your desk (instant access)

REAL-WORLD USE:
```javascript
// Cache user data
async function getUser(userId) {
  // Check Redis first (fast)
  let user = await redis.get(`user:${userId}`);

  if (user) {
    return JSON.parse(user);  // Cache hit! ✅
  }

  // Not in cache, query DB (slow)
  user = await db.query('SELECT * FROM users WHERE id = ?', [userId]);

  // Store in Redis for next time
  await redis.set(`user:${userId}`, JSON.stringify(user), 'EX', 3600);

  return user;
}
```

KEY USE CASES:
1. Caching (most common)
   - User sessions
   - API responses
   - Database query results

2. Rate Limiting
   - Limit API calls per user
   - Prevent abuse

3. Leaderboards
   - Gaming scores
   - Trending posts

4. Real-time Features
   - Online users
   - Live notifications

WHEN TO USE:
✅ Frequently accessed data
✅ Need sub-millisecond response
✅ Temporary data (sessions)
✅ Counters and leaderboards

WHEN NOT TO USE:
❌ Primary database
❌ Large data storage
❌ Complex queries

═══════════════════════════════════════════════════════════════════════════════════════
KAFKA - "The Post Office for Microservices"
═══════════════════════════════════════════════════════════════════════════════════════

WHAT IT DOES:
Message broker that stores and distributes events between services

PROBLEM IT SOLVES:
Service-to-service communication without tight coupling

ANALOGY:
Without Kafka: Phone call (both must be available NOW)
With Kafka: Post office (send anytime, receive anytime)

REAL-WORLD USE:
```javascript
// Producer (Order Service)
async function createOrder(orderData) {
  // Save to database
  await db.saveOrder(orderData);

  // Send event to Kafka (non-blocking)
  await kafka.send({
    topic: 'orders.created',
    messages: [{
      key: orderData.userId,
      value: JSON.stringify(orderData)
    }]
  });

  return { success: true };
}

// Consumer (Email Service)
kafka.subscribe({ topic: 'orders.created' });

kafka.run({
  eachMessage: async ({ message }) => {
    const order = JSON.parse(message.value);
    await sendOrderConfirmationEmail(order);
  }
});

// Consumer (Inventory Service) - reads SAME messages!
kafka.subscribe({ topic: 'orders.created' });

kafka.run({
  eachMessage: async ({ message }) => {
    const order = JSON.parse(message.value);
    await updateInventory(order);
  }
});
```

KEY CONCEPTS:
- Topic: Category of messages (like WhatsApp group)
- Partition: Sub-division for parallel processing
- Producer: Sends messages
- Consumer: Reads messages
- Consumer Group: Multiple consumers sharing workload

WHEN TO USE:
✅ Microservices communication
✅ Event-driven architecture
✅ Real-time data processing
✅ Log aggregation
✅ High throughput (millions of messages/sec)

WHEN NOT TO USE:
❌ Simple request-response
❌ Small scale (<1000 msg/sec)
❌ Need immediate response

═══════════════════════════════════════════════════════════════════════════════════════
CI/CD - "The Automated Delivery Pipeline"
═══════════════════════════════════════════════════════════════════════════════════════

WHAT IT DOES:
Automates the entire software delivery process

PROBLEM IT SOLVES:
Manual deployments are slow, error-prone, and inconsistent

ANALOGY:
Without CI/CD: Manual factory (slow, inconsistent)
With CI/CD: Automated assembly line (fast, consistent)

REAL-WORLD USE:
```yaml
# .github/workflows/deploy.yml
name: CI/CD Pipeline

on:
  push:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - run: npm install
      - run: npm test                    # Run tests

  build:
    needs: test
    runs-on: ubuntu-latest
    steps:
      - run: docker build -t myapp .     # Build Docker image
      - run: docker push myapp           # Push to registry

  deploy:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - run: kubectl apply -f k8s/       # Deploy to Kubernetes
```

COMPLETE FLOW:
1. Developer pushes code to Git
2. CI automatically runs:
   - Code quality checks (ESLint)
   - Unit tests
   - Integration tests
   - Security scans
   - Build Docker image
3. CD automatically deploys:
   - Deploy to staging
   - Run smoke tests
   - Deploy to production (with approval)
   - Monitor metrics

DEPLOYMENT STRATEGIES:
1. Rolling: Replace pods gradually (zero downtime)
2. Blue-Green: Two environments, switch instantly
3. Canary: Test with 5% users, then 100%

WHEN TO USE:
✅ Multiple developers
✅ Frequent deployments
✅ Need fast feedback
✅ Quality is important

COMMON INTERVIEW QUESTIONS (DevOps Overview)
═══════════════════════════════════════════════════════════════════════════════════════

Q1: What is DevOps?

A: "DevOps is a culture and set of practices that combines software
    development (Dev) and IT operations (Ops) to shorten the development
    lifecycle and deliver high-quality software continuously."

Key principles:
- Automation
- Continuous Integration/Deployment
- Monitoring and feedback
- Collaboration between teams

Q2: Explain Docker vs Kubernetes

A: "Docker packages applications into containers, Kubernetes manages
    and orchestrates those containers at scale."

Example:
- Docker: "I have a container with my app"
- Kubernetes: "I'll run 10 copies across 3 servers, load balance them,
               and restart if they crash"

Q3: Why use Redis instead of database for caching?

A: "Redis stores data in memory (RAM) which is 50-100x faster than
    disk-based databases."

Speed comparison:
- Redis: <1ms (memory)
- Database: 10-50ms (disk)
- For frequently accessed data, Redis is essential

Q4: When would you use Kafka vs REST API?

A: "Use Kafka for asynchronous, event-driven communication where services
    don't need immediate response. Use REST API for synchronous,
    request-response communication."

Kafka:
- Order placed → Send event → Multiple services process later
- Services decoupled
- Messages persist

REST API:
- Get user profile → Immediate response needed
- Synchronous
- Direct communication

Q5: What's the most important metric to monitor in production?

A: "Error rate (percentage of failed requests) - it directly impacts
    user experience and indicates health of the system."

Other critical metrics:
- Response time (latency)
- Throughput (requests/second)
- Resource usage (CPU, memory)
- Business metrics (conversions, revenue)

Q6: How do you ensure zero-downtime deployments?

A: "Use Kubernetes rolling updates with health checks and readiness probes."

Process:
1. Start new pods with new version
2. Wait for health checks to pass
3. Gradually shift traffic to new pods
4. Terminate old pods
5. Always keep some old pods running during transition

Q7: What would you do if production deployment fails?

A: "Immediate rollback, then investigate and fix."

Steps:
1. Detect issue (monitoring alerts)
2. Rollback to previous version (kubectl rollout undo)
3. Notify team
4. Investigate root cause
5. Fix in development
6. Test thoroughly
7. Redeploy

Q8: Design a CI/CD pipeline for a microservices application

A: "Multi-stage pipeline with testing, building, and deployment stages."

Pipeline:
1. Source stage: Git push triggers pipeline
2. Test stage:
   - Lint code
   - Run unit tests
   - Run integration tests
3. Build stage:
   - Build Docker images
   - Security scans
   - Push to registry
4. Deploy stage:
   - Deploy to staging
   - Smoke tests
   - Deploy to production (with approval)
5. Monitor stage:
   - Track metrics
   - Auto-rollback if errors
