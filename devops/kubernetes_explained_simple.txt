1. CLUSTER = Entire Kubernetes Setup

Think: Like a data center

A cluster contains:
- 1 Control Plane (Master)
- Multiple Worker Nodes (Servers)

2. CONTROL PLANE (Master Node) = Brain

Components:
- **API Server**: Front door to Kubernetes (all commands go here)
- **Scheduler**: Decides which node runs which pod
- **Controller Manager**: Ensures desired state (keeps things running)
- **etcd**: Database storing cluster state

Analogy: CEO and management team

3. WORKER NODE = Physical/Virtual Server

Each node contains:
- **kubelet**: Agent that manages pods on this node
- **kube-proxy**: Network proxy for services
- **Container Runtime**: Docker/containerd (runs containers)

Analogy: Factory worker

4. POD = Smallest Deployable Unit ⭐ MOST IMPORTANT

Think: Pod is a wrapper around container(s)

┌────────────────────────┐
│        POD             │
│  ┌──────────────────┐  │
│  │   Container 1    │  │ Main app
│  │   (nginx)        │  │
│  └──────────────────┘  │
│                        │
│  ┌──────────────────┐  │
│  │   Container 2    │  │ Sidecar (logging)
│  │   (fluentd)      │  │
│  └──────────────────┘  │
│                        │
│  Shared:               │
│  - Network (localhost) │
│  - Storage volumes     │
│  - Lifecycle           │
└────────────────────────┘

Key Points:
- Pod = One or more containers
- Containers in pod share IP address
- Typically: 1 container per pod
- Pod is ephemeral (can die and restart)

5. DEPLOYMENT = Manages Pods ⭐ SUPER IMPORTANT

Think: Deployment is your desired state

```yaml
# I want 3 replicas of nginx
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deployment
spec:
  replicas: 3  # I want 3 pods
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
      - name: nginx
        image: nginx:1.21
        ports:
        - containerPort: 80
```

Kubernetes ensures:
✅ Always 3 pods running
✅ Auto-restart if pod crashes
✅ Rolling updates (zero downtime)
✅ Rollback if update fails

VISUAL:
┌────────────────────────────────────┐
│      Deployment: nginx             │
│      Desired: 3 replicas           │
└────────┬───────────────────────────┘
         │ Creates/Manages
         ▼
    ┌────┴────┬─────────┐
    ▼         ▼         ▼
┌────────┐ ┌────────┐ ┌────────┐
│ Pod 1  │ │ Pod 2  │ │ Pod 3  │
│ nginx  │ │ nginx  │ │ nginx  │
└────────┘ └────────┘ └────────┘

If Pod 2 crashes:
Kubernetes: "I need 3 pods, only 2 running, creating new one..."
→ Automatically creates Pod 4 ✅

6. SERVICE = Stable Network Endpoint

Think: Like a load balancer

PROBLEM: Pods have dynamic IPs (change when restarted)

┌────────┐  IP: 10.0.1.5
│ Pod 1  │  Crashes and restarts...
└────────┘  IP: 10.0.1.8  (Changed!)

How do other apps connect? 🤔

SOLUTION: Service (stable IP + DNS name)

┌────────────────────────────────┐
│   Service: nginx-service       │
│   IP: 10.0.100.50 (stable)    │
│   DNS: nginx-service.default  │
└────────┬───────────────────────┘
         │ Load balances to
    ┌────┴────┬─────────┐
    ▼         ▼         ▼
┌────────┐ ┌────────┐ ┌────────┐
│ Pod 1  │ │ Pod 2  │ │ Pod 3  │
└────────┘ └────────┘ └────────┘

Pods can die/restart, Service IP stays same!

```yaml
apiVersion: v1
kind: Service
metadata:
  name: nginx-service
spec:
  selector:
    app: nginx  # Targets pods with label app=nginx
  ports:
  - port: 80
    targetPort: 80
  type: LoadBalancer  # Expose externally
```

Service Types:
- **ClusterIP**: Internal only (default)
- **NodePort**: Expose on node's port
- **LoadBalancer**: Cloud load balancer (AWS ELB, GCP LB)
- **ExternalName**: DNS alias

8. ConfigMap & Secret = Configuration

**ConfigMap**: Non-sensitive configuration

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  API_URL: "https://api.example.com"
  LOG_LEVEL: "info"
  MAX_CONNECTIONS: "100"
```

**Secret**: Sensitive data (passwords, keys)

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: db-secret
type: Opaque
data:
  password: cGFzc3dvcmQxMjM=  # base64 encoded
  username: YWRtaW4=
```

Use in Pod:
```yaml
spec:
  containers:
  - name: app
    image: myapp
    env:
    - name: API_URL
      valueFrom:
        configMapKeyRef:
          name: app-config
          key: API_URL
    - name: DB_PASSWORD
      valueFrom:
        secretKeyRef:
          name: db-secret
          key: password
```

9. VOLUME = Persistent Storage

Types:
- **emptyDir**: Temporary (dies with pod)
- **hostPath**: Node's filesystem
- **PersistentVolume (PV)**: Cluster-wide storage
- **PersistentVolumeClaim (PVC)**: Request for storage

Example:
```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: db-storage
spec:
  accessModes:
  - ReadWriteOnce
  resources:
    requests:
      storage: 10Gi
```

Use in Pod:
```yaml
spec:
  volumes:
  - name: data
    persistentVolumeClaim:
      claimName: db-storage
  containers:
  - name: postgres
    image: postgres:14
    volumeMounts:
    - name: data
      mountPath: /var/lib/postgresql/data
```

10. INGRESS = HTTP/HTTPS Router

Think: Like Nginx reverse proxy

┌────────────────────────────────────────┐
│            Internet                    │
└────────────┬───────────────────────────┘
             │
             ▼
┌────────────────────────────────────────┐
│         Ingress Controller             │
│         (Nginx/Traefik)                │
└────────┬────────────────┬──────────────┘
         │                │
         │ /api           │ /web
         ▼                ▼
    ┌─────────┐      ┌──────────┐
    │ API     │      │ Frontend │
    │ Service │      │ Service  │
    └─────────┘      └──────────┘

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: main-ingress
spec:
  rules:
  - host: example.com
    http:
      paths:
      - path: /api
        pathType: Prefix
        backend:
          service:
            name: api-service
            port:
              number: 80
      - path: /web
        pathType: Prefix
        backend:
          service:
            name: frontend-service
            port:
              number: 80
```

PART 3: HOW KUBERNETES WORKS (Step by Step)
═══════════════════════════════════════════════════════════════════════════════════════

SCENARIO: Deploying an Application

STEP 1: You create a deployment

```bash
kubectl create deployment nginx --image=nginx:1.21 --replicas=3
```

Or using YAML:
```yaml
# nginx-deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
      - name: nginx
        image: nginx:1.21
        ports:
        - containerPort: 80
```

```bash
kubectl apply -f nginx-deployment.yaml
```

STEP 2: Request goes to API Server

┌──────────┐
│   You    │  kubectl apply
└────┬─────┘
     │
     ▼
┌──────────────┐
│  API Server  │  "New deployment request received"
└──────┬───────┘
       │
       ▼
┌──────────────┐
│    etcd      │  Save desired state: 3 nginx pods
└──────────────┘

STEP 3: Scheduler assigns pods to nodes

┌──────────────┐
│  Scheduler   │  "Which nodes have resources?"
└──────┬───────┘
       │ Checks: CPU, memory, affinity rules
       │
       ▼
┌──────────────────────────────────┐
│  Decision:                       │
│  - Pod 1 → Node 1 (has 2GB RAM) │
│  - Pod 2 → Node 2 (has 2GB RAM) │
│  - Pod 3 → Node 3 (has 2GB RAM) │
└──────────────────────────────────┘

STEP 4: kubelet on each node creates containers

Node 1:
┌────────────────┐
│   kubelet      │  "I need to create nginx pod"
└────┬───────────┘
     │
     ▼
┌────────────────┐
│ Container      │  Pull nginx:1.21 image
│ Runtime        │  Create container
│ (Docker)       │  Start container
└────────────────┘

STEP 5: Controller Manager monitors state

┌──────────────────────┐
│ Controller Manager   │  "Are 3 pods running?"
└──────┬───────────────┘
       │ Continuously checks
       │
       ▼
Current state: 3 pods running ✅
Desired state: 3 pods
Status: OK ✅

If Pod crashes:
Current state: 2 pods running ❌
Desired state: 3 pods
Action: Create new pod ✅

COMPLETE FLOW VISUAL:

1. You: kubectl apply
         │
         ▼
2. API Server: Save to etcd
         │
         ▼
3. Scheduler: Assign to nodes
         │
         ▼
4. kubelet: Create containers
         │
         ▼
5. Controller: Monitor & maintain
         │
         ▼
6. ✅ 3 pods running!

SCENARIO 3: Health Check Failures

Define health checks:
```yaml
spec:
  containers:
  - name: app
    image: myapp
    livenessProbe:   # Is container alive?
      httpGet:
        path: /health
        port: 8080
      initialDelaySeconds: 30
      periodSeconds: 10
    readinessProbe:  # Is container ready for traffic?
      httpGet:
        path: /ready
        port: 8080
      initialDelaySeconds: 5
      periodSeconds: 5
```

Timeline:
10:00 - App starts, health check: ✅
10:01 - Health check: ✅
10:02 - App hangs, health check: ❌
10:02:10 - Health check: ❌ (2nd failure)
10:02:20 - Health check: ❌ (3rd failure)
10:02:21 - Kubernetes: "Container unhealthy, RESTARTING!"
10:02:25 - New container started ✅

SCENARIO 4: Resource Exhaustion

```yaml
spec:
  containers:
  - name: app
    resources:
      requests:    # Minimum needed
        cpu: "100m"
        memory: "128Mi"
      limits:      # Maximum allowed
        cpu: "500m"
        memory: "512Mi"
```

App tries to use 1GB memory:
┌────────────────────────────────┐
│         Pod                    │
│  Memory usage: 512MB → 1GB     │
│  Limit: 512MB                  │
│  Status: OOMKilled (killed!)   │
└────────────────────────────────┘

Kubernetes: "Pod killed due to OOM, restarting..."

New pod starts with fresh memory ✅

Scale to 5:
┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐

└────────┘ └────────┘ └────────┘ └────────┘ └────────┘

2. HORIZONTAL POD AUTOSCALER (HPA) ⭐ AUTOMATIC

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: nginx-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: nginx
  minReplicas: 2
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70  # Keep CPU at 70%
```

How it works:

Normal traffic (CPU: 30%):
┌────────┐ ┌────────┐
│ Pod 1  │ │ Pod 2  │  2 pods (minimum)
└────────┘ └────────┘

Traffic increases (CPU: 80%):
HPA: "CPU is 80%, above 70% target, SCALING UP!"

┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐
│ Pod 1  │ │ Pod 2  │ │ Pod 3  │ │ Pod 4  │  4 pods
└────────┘ └────────┘ └────────┘ └────────┘
CPU now: 40% ✅

Traffic decreases (CPU: 20%):
HPA: "CPU is 20%, below 70% target, SCALING DOWN!"

┌────────┐ ┌────────┐
│ Pod 1  │ │ Pod 2  │  Back to 2 pods
└────────┘ └────────┘

3. VERTICAL POD AUTOSCALER (VPA)

Adjusts CPU/memory requests automatically

```yaml
apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata:
  name: nginx-vpa
spec:
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: nginx
  updatePolicy:
    updateMode: "Auto"
```

Before:
┌─────────────────┐
│      Pod        │
│  CPU: 100m      │  Too small, pod throttled
│  Memory: 128Mi  │
└─────────────────┘

VPA adjusts:

Q1: What is Kubernetes and why use it?

A: "Kubernetes is a container orchestration platform that automates
    deployment, scaling, and management of containerized applications.
    It solves the problem of managing hundreds or thousands of containers
    across multiple servers."

Benefits:
✅ Automated deployment and scaling
✅ Self-healing (auto-restart failed containers)
✅ Load balancing
✅ Zero-downtime deployments
✅ Service discovery
✅ Resource optimization
✅ Multi-cloud portability

Q2: What is a Pod and why not just use containers?

A: "A Pod is the smallest deployable unit in Kubernetes. It's a wrapper
    around one or more containers that share network and storage."

Why Pods?
- Containers in a pod share localhost (can communicate easily)
- Atomic deployment (all containers start/stop together)
- Shared volumes
- Simplified networking

Example: Main app + logging sidecar in same pod

Q3: What's the difference between Deployment and StatefulSet?

A: "Deployment is for stateless apps, StatefulSet is for stateful apps"

┌──────────────────┬─────────────────┬──────────────────┐
│   Feature        │  Deployment     │  StatefulSet     │
├──────────────────┼─────────────────┼──────────────────┤
│ Pod names        │ Random          │ Predictable      │
│                  │ nginx-abc123    │ mysql-0, mysql-1 │
├──────────────────┼─────────────────┼──────────────────┤
│ Order            │ No guarantee    │ Ordered          │
│                  │ Create/delete   │ Create: 0→1→2    │
│                  │ any order       │ Delete: 2→1→0    │
├──────────────────┼─────────────────┼──────────────────┤
│ Storage          │ Shared          │ Dedicated per pod│
├──────────────────┼─────────────────┼──────────────────┤
│ Use case         │ Web apps, APIs  │ Databases, Kafka │
└──────────────────┴─────────────────┴──────────────────┘

Q4: How does Kubernetes handle secrets?

A: "Secrets store sensitive data (passwords, tokens) encoded in base64"

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: db-secret
type: Opaque
data:
  password: cGFzc3dvcmQxMjM=  # base64 encoded
```

Best practices:
✅ Use RBAC (limit who can read secrets)
✅ Enable encryption at rest (in etcd)
✅ Use external secret managers (Vault, AWS Secrets Manager)
✅ Never commit secrets to Git
✅ Use Sealed Secrets or External Secrets Operator

Q5: What is a Service and why do we need it?

A: "Service provides a stable IP and DNS name for a set of pods"

Problem: Pods have dynamic IPs (change on restart)
Solution: Service acts as a load balancer with stable endpoint

Types:
1. **ClusterIP**: Internal only (default)
2. **NodePort**: Exposes on node's port (30000-32767)
3. **LoadBalancer**: Cloud load balancer (AWS ELB, GCP LB)
4. **ExternalName**: DNS alias

Q6: How does Kubernetes achieve high availability?

A: "Multiple control plane nodes and worker nodes across availability zones"

```
│  └──────────────┘  └──────────────┘     │
└──────────────────────────────────────────┘
```

Features:
- etcd cluster (distributed database)
- Multiple API servers (load balanced)
- Controller replication
- Pod anti-affinity (spread across nodes/zones)

Q7: What are Readiness and Liveness probes?

A: "Health checks that determine if container is ready and alive"

**Liveness Probe**: Is container alive?
- Failure → Restart container

**Readiness Probe**: Is container ready for traffic?
- Failure → Remove from service endpoints (no traffic)

**Startup Probe**: Has container started?
- Used for slow-starting apps

```yaml
livenessProbe:
  httpGet:
    path: /health
    port: 8080
  initialDelaySeconds: 30
  periodSeconds: 10
  failureThreshold: 3

readinessProbe:
  httpGet:
    path: /ready
    port: 8080
  initialDelaySeconds: 5
  periodSeconds: 5
  failureThreshold: 3
```

Q8: How does rolling update work?

A: "Gradually replace old pods with new ones to achieve zero downtime"

Process:
1. Create 1 new pod (v2)
2. Wait for readiness check to pass
3. Terminate 1 old pod (v1)
4. Repeat until all pods updated

Control:
```yaml
rollingUpdate:
  maxSurge: 1        # Max 1 extra pod during update
  maxUnavailable: 0  # No pod downtime
```

Q9: What is a DaemonSet?

A: "DaemonSet runs one pod on every node (or selected nodes)"

Use cases:
- Log collectors (Fluentd, Logstash)
- Monitoring agents (Prometheus Node Exporter)
- Network plugins (Calico, Weave)
- Storage daemons (Ceph, GlusterFS)

```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: fluentd
spec:
  selector:
    matchLabels:
      app: fluentd
  template:
    metadata:
      labels:
        app: fluentd
    spec:
      containers:
      - name: fluentd
        image: fluentd:latest
```

Q10: How does Horizontal Pod Autoscaler (HPA) work?

A: "HPA automatically scales pods based on CPU/memory/custom metrics"

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: api-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: api
  minReplicas: 2
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70
```

How it works:
1. HPA checks metrics every 15 seconds (default)
2. If CPU > 70%, increase replicas
3. If CPU < 70%, decrease replicas
4. Respects min/max limits
5. Cooldown period (prevent thrashing)

Q11: What are Taints and Tolerations?

A: "Taints repel pods from nodes, Tolerations allow pods on tainted nodes"

Use case: Dedicated nodes for specific workloads

```bash
# Taint node (no pods allowed except with toleration)
kubectl taint nodes node-1 gpu=true:NoSchedule
```

```yaml
# Pod with toleration (can run on tainted node)
spec:
  tolerations:
  - key: "gpu"
    operator: "Equal"
    value: "true"
    effect: "NoSchedule"
```

Effects:
- **NoSchedule**: Don't schedule new pods
- **PreferNoSchedule**: Try to avoid scheduling
- **NoExecute**: Evict existing pods

Q12: What is the difference between ConfigMap and Secret?

A: "Both store configuration, but Secrets are for sensitive data"

KUBERNETES NETWORKING RULES:

1. Every pod gets its own IP address
2. Pods can communicate with all other pods without NAT
3. Agents on a node can communicate with all pods on that node

NETWORK POLICIES:

Control traffic between pods

PART 11: KUBERNETES BEST PRACTICES
═══════════════════════════════════════════════════════════════════════════════════════

1. RESOURCE LIMITS ⭐ CRITICAL

```yaml
resources:
  requests:    # Minimum guaranteed
    cpu: "100m"
    memory: "128Mi"
  limits:      # Maximum allowed
    cpu: "500m"
    memory: "512Mi"
```

Why:
✅ Prevents resource starvation
✅ Better scheduling decisions
✅ Protects from runaway processes

2. HEALTH CHECKS

Always define:
```yaml
livenessProbe:   # Restart if unhealthy
  httpGet:
    path: /health
    port: 8080
  initialDelaySeconds: 30
  periodSeconds: 10

readinessProbe:  # Remove from service if not ready
  httpGet:
    path: /ready
    port: 8080
  initialDelaySeconds: 5
  periodSeconds: 5
```

3. USE NAMESPACES

```bash
# Separate environments
kubectl create namespace development
kubectl create namespace staging
kubectl create namespace production
```

4. LABELS & SELECTORS

```yaml
metadata:
  labels:
    app: nginx
    environment: production
    tier: frontend
    version: v1.0.0
```

Benefits:
- Organize resources
- Select with kubectl
- Service discovery
- Network policies

5. ROLLING UPDATE STRATEGY

```yaml
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 1
    maxUnavailable: 0  # Zero downtime!
```

6. USE CONFIGMAP/SECRET FOR CONFIGURATION

DON'T hardcode:
```yaml
# Bad ❌
env:
- name: API_URL
  value: "https://api.example.com"
```

DO use ConfigMap:
```yaml
# Good ✅
env:
- name: API_URL
  valueFrom:
    configMapKeyRef:
      name: app-config
      key: API_URL
```

7. SECURITY

```yaml
spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 1000
    fsGroup: 1000
    capabilities:
      drop:
      - ALL
    readOnlyRootFilesystem: true
```

8. RESOURCE QUOTAS

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: dev-quota
  namespace: development
spec:
  hard:
    requests.cpu: "10"
    requests.memory: 20Gi
    persistentvolumeclaims: "10"
    pods: "50"
```

9. POD DISRUPTION BUDGET

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: api-pdb
spec:
  minAvailable: 2  # Always keep 2 pods running
  selector:
    matchLabels:
      app: api
```

10. AFFINITY & ANTI-AFFINITY

Spread pods across nodes:
```yaml
spec:
  affinity:
    podAntiAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchLabels:
            app: api
        topologyKey: kubernetes.io/hostname
```

This ensures API pods are on different nodes (high availability)

PRACTICE SCENARIO:
"You have a Node.js API that needs high availability and auto-scaling"

Solution:
```yaml
# Deployment with 3 replicas
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
spec:
  replicas: 3
  template:
    spec:
      containers:
      - name: api
        image: myapi:v1.0.0
        resources:
          requests:
            cpu: "100m"

          httpGet:
            path: /health
            port: 8080

apiVersion: v1
kind: Service
metadata:
  name: api
spec:
  selector:
    app: api
  type: LoadBalancer

# HPA for auto-scaling
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: api-hpa
spec:
  scaleTargetRef:
    kind: Deployment
    name: api
  minReplicas: 3
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        averageUtilization: 70
```

This shows understanding of:
✅ High availability (3 replicas)
✅ Load balancing (Service)
✅ Auto-scaling (HPA)
✅ Health checks (liveness probe)
✅ Resource management (requests)
