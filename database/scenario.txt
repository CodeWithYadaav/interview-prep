✅ Solution: Use streams + batch inserts:

const csv = require('csv-parser');

    batch = [];
  }
});

3. Pooling in Databases

Problem: Opening new DB connection for every request is slow and wasteful.
✅ Solution: Use connection pooling

Connection Pooling is a technique where a pool (cache) of database connections is maintained and reused, instead of creating and closing DB connections on every request.

const { Pool } = require('pg');
const pool = new Pool({ max: 10 });

const result = await pool.query('SELECT * FROM users');


In NestJS
@Module({
  imports: [
    TypeOrmModule.forRoot({
      type: 'postgres',
      host: 'localhost',
      port: 5432,
      username: 'user',
      password: 'pass',
      database: 'mydb',
      synchronize: true,
      poolSize: 10
    })
  ],
})



❌ What Happens If Pooling is NOT Used?
🔁 New DB Connection for Every Request
Every API call creates a fresh DB connection, which:
Takes time to authenticate
Consumes DB server resources
Increases latency


💣 High Resource Consumption
      Opening/closing DB connections repeatedly is expensive.
      Without pooling, CPU and memory usage on both app & DB servers can spike.

⏳ Performance Bottlenecks
      Your app might slow down or even hang under load.
      Creating a DB connection is 5x to 20x slower than reusing an existing one.

📛 Hitting Connection Limits
      Most DBs (e.g., PostgreSQL, MySQL) have a max connection limit.
      Without pooling, you may exhaust DB connections, causing:
              Timeout errors
              Refused connections
              Crashes







4. Handling Slow Queries (Indexing Best Practices,limit/offset ,sharding)

🔸 a. Indexing Best Practices
        Index columns used in WHERE, JOIN, ORDER BY.
        Don’t over-index (writes get slower).
        Composite indexes: (status, created_at)

->CREATE INDEX idx_status_created ON orders(status, created_at);


🔸 b. Limit/Offset
        Use LIMIT + OFFSET for pagination but not for large data (slow at high offsets).

SELECT * FROM users ORDER BY id LIMIT 10 OFFSET 100;

✅ Prefer cursor-based pagination for better performance.

🔸 c. Sharding
        Split data across DBs by user_id % 2 or regions.
        Useful when single DB hits vertical limits.









5. Normalisation

Goal: Avoid duplicate data, make updates consistent.
Example: Product and Category
            Product table: id, name, category_id
            Category table: id, name
Instead of storing category_name inside every product row.

✅ Use 3rd Normal Form (3NF):
    Every non-key depends only on the key.

##How indexing works in mysql/postgres

An index is like a book's table of contents. It speeds up data retrieval by avoiding full table scans.

🧠 Simple Analogy:
Imagine a phonebook 📕 with names in alphabetical order. To find "Ravi", you don't flip every page — you jump directly to "R". That’s what an index does.

🧠 How It Works Behind the Scenes

1. What is stored?
  When you index a column (name, id, etc.), the DB engine:
      Creates a sorted copy of that column (usually using a B-Tree or Hash Table depending on the index type).
      Stores a pointer to the full row where that data lives.



2. What happens when you run a query?
If your query uses a WHERE, JOIN, or ORDER BY on an indexed column:
      It uses the index tree to directly locate rows.
      Skips scanning unneeded rows.




⚙️ Internals: How It Works
🔹 MySQL (InnoDB) and PostgreSQL both use:
        B-Tree (Balanced Tree) for most indexing
        Allows log(n) search time
        Maintains sorted order of keys

📍When We Query:
SELECT * FROM users WHERE email = 'x@example.com';


Without index:
            Full table scan (check every row)

With index:
            Jumps directly to the row via B-Tree
            Skips unrelated rows



🔍 Index Types (Basics):
            | Index Type          | Use Case                             |
| ------------------- | ------------------------------------ |
| **Primary Index**   | Automatically created on primary key |
| **Unique Index**    | Ensures uniqueness of a column       |
| **Composite Index** | Index on multiple columns            |
| **Partial Index**   | (Postgres only) Index subset of rows |
| **Full-Text Index** | For fast text search                 |
| **GIN/Hash**        | (Postgres) for JSONB, arrays, etc.   |



⚠️ When Not to Use Index:

For columns with lots of duplicate values (like gender, isActive)
On frequently updated columns (because index maintenance is costly)
If the table is small — index doesn’t add value



🧪 Example in MySQL/Postgres
📦 Create Index
CREATE INDEX idx_email ON users(email);


📊 View Indexes

-- MySQL
SHOW INDEXES FROM users;

-- PostgreSQL
SELECT * FROM pg_indexes WHERE tablename = 'users';


⚡ Performance Comparison

| Without Index   | With Index       |
| --------------- | ---------------- |
| 100,000 rows    | 100,000 rows     |
| Query took 4.2s | Query took 0.05s |




✅ Real-world Advice
Always index columns used in:
                WHERE
                    JOIN ON
                        ORDER BY
                            GROUP BY

Use composite index if multiple filters used together
Monitor with EXPLAIN or EXPLAIN ANALYZE to see index usage
