1️⃣ WHAT PROBLEM DOES NESTJS SOLVE?
════════════════════════════════════════════════════════════════════════════════════

🎯 THE PROBLEM:
Raw Node.js/Express apps become MESSY as they grow:
❌ No structure → Code scattered everywhere
❌ Manual dependency management → new DatabaseService() everywhere
❌ No built-in patterns → Everyone codes differently
❌ Hard to test → Tightly coupled code
❌ No TypeScript enforcement → Runtime errors

✅ NESTJS SOLUTION:
Provides OPINIONATED ARCHITECTURE out of the box:
✅ Modular structure (like Angular for backend)
✅ Built-in Dependency Injection
✅ TypeScript-first (type safety everywhere)
✅ Decorators for clean, declarative code
✅ Built-in Guards, Interceptors, Pipes, Middleware
✅ Testability (easy to mock/inject)

🗣️ INTERVIEW ANSWER:
"NestJS solves the problem of building scalable, maintainable Node.js applications. 
It provides an opinionated architecture with built-in dependency injection, modular 
structure, and TypeScript support, which makes large applications easier to manage, 
test, and scale compared to plain Express."

2️⃣ INVERSION OF CONTROL (IoC)
════════════════════════════════════════════════════════════════════════════════════

🧠 SIMPLE EXPLANATION:
Instead of YOU creating dependencies, the FRAMEWORK creates them for you.

🏪 REAL-WORLD ANALOGY:
Traditional approach (you control):
  You go to store → Buy ingredients → Cook food → Eat
  (You control everything)

IoC approach (framework controls):
  You order food → Restaurant handles everything → Food arrives
  (You don't control HOW it's made)

📝 CODE COMPARISON:

❌ WITHOUT IoC (Manual control):
class UserService {
  private db = new Database();  // YOU create it
  private logger = new Logger(); // YOU create it
}

✅ WITH IoC (Framework control):
@Injectable()
class UserService {
  constructor(
    private db: Database,      // NestJS creates & injects
    private logger: Logger     // NestJS creates & injects
  ) {}
}

💡 KEY BENEFITS:
• Loose coupling (classes don't create dependencies)
• Easy testing (inject mocks)
• Reusability (share instances)

🗣️ INTERVIEW ANSWER:
"IoC is when the framework controls object creation instead of you doing it manually. 
In NestJS, instead of using 'new' to create dependencies, we mark classes with 
@Injectable() and let NestJS handle instantiation and injection through constructors."

3️⃣ DEPENDENCY INJECTION (DI)
════════════════════════════════════════════════════════════════════════════════════

🧠 SIMPLE EXPLANATION:
Dependency Injection is HOW IoC is implemented. Classes receive their dependencies 
from outside (injected) rather than creating them.

📊 FLOW DIAGRAM:
┌──────────────┐
│ AppModule    │ ← Defines what's available
│ providers: [ │
│   Database,  │
│   Logger     │
│ ]            │
└──────┬───────┘
       │ NestJS IoC Container
       ↓
┌──────────────┐
│ UserService  │ ← Receives dependencies automatically
│ constructor( │
│   Database,  │ ← Injected!
│   Logger     │ ← Injected!
│ )            │
└──────────────┘

🔧 THREE TYPES OF INJECTION:

1. Constructor Injection (Most Common ✅)
@Injectable()
export class UserService {
  constructor(private readonly userRepo: UserRepository) {}
  // userRepo is automatically injected
}

2. Property Injection (Rare)
@Injectable()
export class UserService {
  @Inject(UserRepository)
  private readonly userRepo: UserRepository;
}

3. Custom Token Injection
@Injectable()
export class UserService {
  constructor(@Inject('DATABASE_CONNECTION') private db: any) {}
}

🗣️ INTERVIEW ANSWER:
"Dependency Injection is a design pattern where classes receive their dependencies 
from outside rather than creating them. In NestJS, we use constructor injection - 
dependencies are declared in the constructor and automatically provided by the 
framework based on what's registered in the module's providers array."

4️⃣ WHY ARE SERVICES SINGLETON BY DEFAULT?
════════════════════════════════════════════════════════════════════════════════════

🧠 SIMPLE EXPLANATION:
Singleton means only ONE INSTANCE of a service exists across the entire application.

🏢 REAL-WORLD ANALOGY:
Your office has ONE printer (singleton):
• Everyone uses the SAME printer
• No need for 100 printers (wasteful!)
• State is shared (print queue is shared)

📝 EXAMPLE:

@Injectable()
export class UserService {
  private cache = [];  // Shared across all usages!
  
  addToCache(data) {
    this.cache.push(data);
  }
}

// In Controller A
userService.addToCache('A');

// In Controller B (SAME INSTANCE!)
userService.cache // Contains 'A'

💡 WHY SINGLETON?

| Reason            | Explanation                                     |
|-------------------|-------------------------------------------------|
| Memory Efficient  | One instance instead of thousands               |
| State Sharing     | Share data (caches, connections) across app     |
| Performance       | No overhead of creating multiple instances      |
| Connection Pools  | Database connections are shared, not duplicated |

⚠️ WHEN NOT SINGLETON?
Use REQUEST-SCOPED providers for:
• User-specific data (current user, session)
• Request tracking
• Per-request caching

@Injectable({ scope: Scope.REQUEST })
export class RequestLogger {
  // New instance per HTTP request
}

🗣️ INTERVIEW ANSWER:
"Services are singleton by default for performance and memory efficiency. NestJS 
creates ONE instance of each service when the application starts and reuses it 
everywhere. This is ideal for stateless services and sharing resources like 
database connections. For user-specific data, we can use REQUEST scope."

5️⃣ CIRCULAR DEPENDENCY & forwardRef()
════════════════════════════════════════════════════════════════════════════════════

🧠 WHAT IS CIRCULAR DEPENDENCY?

When two classes depend on EACH OTHER:

UserService needs PostService
PostService needs UserService  ← Circular!

💥 THE PROBLEM:

// user.service.ts
@Injectable()
export class UserService {
  constructor(private postService: PostService) {}  // Needs PostService
}

// post.service.ts
@Injectable()
export class PostService {
  constructor(private userService: UserService) {}  // Needs UserService
}

❌ NestJS Error: "Nest can't resolve dependencies..."

🔧 SOLUTION: forwardRef()

forwardRef() tells NestJS: "This dependency will be defined later, trust me!"

✅ FIX WITH forwardRef():

// user.service.ts
@Injectable()
export class UserService {
  constructor(
    @Inject(forwardRef(() => PostService))  // ← Forward reference!
    private postService: PostService
  ) {}
}

// post.service.ts
@Injectable()
export class PostService {
  constructor(
    @Inject(forwardRef(() => UserService))  // ← Forward reference!
    private userService: UserService
  ) {}
}

🧠 HOW IT WORKS:

Normal DI: NestJS evaluates classes immediately
forwardRef: Delays evaluation until runtime (lazy resolution)

Step 1: NestJS sees UserService needs PostService (but it's not ready yet)
Step 2: forwardRef() says "I'll give you a reference later"
Step 3: Once both are created, references are resolved

⚠️ BEST PRACTICE:

Circular dependencies are a CODE SMELL! They indicate poor design.

Better solutions:
1. Extract shared logic into a 3rd service
2. Use events/message queues (loose coupling)
3. Redesign architecture

Example:
UserService → SharedService ← PostService
(No circular dependency!)

🗣️ INTERVIEW ANSWER:
"Circular dependency is when two classes depend on each other, creating a cycle. 
NestJS can't resolve this during initialization. We use forwardRef() to delay 
dependency resolution until runtime. However, circular dependencies are usually 
a design smell, and it's better to refactor by extracting shared logic into a 
separate service."

6️⃣ GUARDS
════════════════════════════════════════════════════════════════════════════════════

🧠 SIMPLE EXPLANATION:
Guards are GATEKEEPERS that decide: "Should this request be allowed?"

🚪 REAL-WORLD ANALOGY:
Security guard at a club:
• Checks your ID (Authentication)
• Checks if you're on VIP list (Authorization)
• Allows entry or denies

📊 REQUEST FLOW:

Client Request
     ↓
  GUARD  ← "Can this request proceed?"
     ↓ (returns true/false)
  Controller ← If true
     ↓
  Service

🔧 CODE EXAMPLE:

@Injectable()
export class AuthGuard implements CanActivate {
  canActivate(context: ExecutionContext): boolean {
    const request = context.switchToHttp().getRequest();
    const token = request.headers['authorization'];
    
    if (!token) {
      return false;  // ❌ Block request
    }
    
    // Verify token...
    return true;  // ✅ Allow request
  }
}

// Usage
@Controller('users')
export class UserController {
  @Get('profile')
  @UseGuards(AuthGuard)  // ← Applied here
  getProfile() {
    return { user: 'data' };
  }
}

💡 COMMON USE CASES:
• Authentication (is user logged in?)
• Authorization (does user have permission?)
• Rate limiting
• Feature flags
• IP whitelisting

🗣️ INTERVIEW ANSWER:
"Guards are classes that implement CanActivate interface to control whether a 
request can proceed. They're executed BEFORE the route handler and return true 
to allow or false to deny. Common use cases are authentication and authorization. 
We apply them using @UseGuards() decorator."

7️⃣ INTERCEPTORS
════════════════════════════════════════════════════════════════════════════════════

🧠 SIMPLE EXPLANATION:
Interceptors can modify BOTH the incoming request AND outgoing response.

🎬 REAL-WORLD ANALOGY:
Instagram filter:
• You take a photo (request)
• Filter processes it (interceptor)
• Enhanced photo comes out (response)

📊 REQUEST/RESPONSE FLOW:

Client Request
     ↓
  GUARD (check permission)
     ↓
  INTERCEPTOR (before) ← Transform request, log, etc.
     ↓
  Controller/Service
     ↓
  INTERCEPTOR (after) ← Transform response, log, cache
     ↓
  Client Response

🔧 CODE EXAMPLE - LOGGING:

@Injectable()
export class LoggingInterceptor implements NestInterceptor {
  intercept(context: ExecutionContext, next: CallHandler): Observable<any> {
    const now = Date.now();
    console.log('Before handler...');
    
    return next.handle().pipe(
      tap(() => {
        console.log(`After handler... ${Date.now() - now}ms`);
      })
    );
  }
}

🔧 CODE EXAMPLE - RESPONSE TRANSFORMATION:

@Injectable()
export class TransformInterceptor implements NestInterceptor {
  intercept(context: ExecutionContext, next: CallHandler): Observable<any> {
    return next.handle().pipe(
      map(data => ({
        success: true,
        timestamp: new Date().toISOString(),
        data: data  // Wrap response in a standard format
      }))
    );
  }
}

// Before: { name: "Alice" }
// After: { success: true, timestamp: "2026-01-14...", data: { name: "Alice" } }

💡 COMMON USE CASES:
• Logging (request/response times)
• Response transformation (wrap all responses)
• Caching
• Error mapping
• Timeout handling
• Metrics collection

🗣️ INTERVIEW ANSWER:
"Interceptors can intercept and modify both requests and responses. They implement 
NestInterceptor interface and have access to the execution context before and after 
the route handler. Common uses include logging, response transformation, and caching. 
They use RxJS observables to handle the response stream."

8️⃣ EXECUTION CONTEXT
════════════════════════════════════════════════════════════════════════════════════

🧠 SIMPLE EXPLANATION:
ExecutionContext is an object that gives you INFORMATION about the current request 
being processed.

📦 WHAT'S INSIDE:
• HTTP request details
• Current handler (controller method)
• Current class (controller)
• Request/response objects
• Custom metadata

🔧 REAL-WORLD ANALOGY:
Like a case file that travels with a request:
• Who made the request?
• Which endpoint was called?
• What's the HTTP method?
• Any special flags/metadata?

📊 CONTEXT HIERARCHY:

ExecutionContext
     ↓
ArgumentsHost ← Access to request/response
     ↓
switchToHttp() → HttpArgumentsHost
     ↓
  getRequest()  ← Get Express request object
  getResponse() ← Get Express response object
  getNext()     ← Get next function

🔧 CODE EXAMPLES:

1. In a Guard:
@Injectable()
export class AuthGuard implements CanActivate {
  canActivate(context: ExecutionContext): boolean {
    // Get HTTP request object
    const request = context.switchToHttp().getRequest();
    const token = request.headers['authorization'];
    
    // Get handler info
    const handler = context.getHandler();
    const className = context.getClass().name;
    
    console.log(`${className}.${handler.name}() called`);
    return !!token;
  }
}

2. In an Interceptor:
@Injectable()
export class LoggingInterceptor implements NestInterceptor {
  intercept(context: ExecutionContext, next: CallHandler) {
    const request = context.switchToHttp().getRequest();
    const { method, url } = request;
    
    console.log(`${method} ${url}`);
    return next.handle();
  }
}

3. Access Custom Metadata:
// Decorator
export const Roles = (...roles: string[]) => SetMetadata('roles', roles);

// Guard using context
@Injectable()
export class RolesGuard implements CanActivate {
  constructor(private reflector: Reflector) {}
  
  canActivate(context: ExecutionContext): boolean {
    // Get metadata from decorator
    const roles = this.reflector.get<string[]>('roles', context.getHandler());
    const request = context.switchToHttp().getRequest();
    
    return this.validateRoles(roles, request.user);
  }
}

💡 WHY IT'S USEFUL:
• Universal API (works for HTTP, WebSocket, gRPC, etc.)
• Access request/response in Guards/Interceptors
• Read custom metadata from decorators
• Get current handler/class information

🗣️ INTERVIEW ANSWER:
"ExecutionContext is an object that provides information about the current request 
being handled. It's used in Guards, Interceptors, and Exception Filters to access 
the request/response objects, current handler, and custom metadata. We use 
context.switchToHttp().getRequest() to get the HTTP request object."

════════════════════════════════════════════════════════════════════════════════════

┌──────────────┬─────────────────────┬──────────────────────────┬────────────────┐
│ Component    │ When It Runs        │ Purpose                  │ Returns        │
├──────────────┼─────────────────────┼──────────────────────────┼────────────────┤
│ Middleware   │ Before routing      │ General request handling │ void / next()  │
│ Guard        │ After middleware    │ Authorization/Auth       │ true/false     │
│ Interceptor  │ Before & After      │ Transform request/response│ Observable    │
│ Pipe         │ Before handler      │ Validation/Transform data│ Transformed val│

│ Filter       │                     │                          │                │
└──────────────┴─────────────────────┴──────────────────────────┴────────────────┘

REQUEST LIFECYCLE (Order of execution):
1. Middleware
2. Guards
3. Interceptors (before)
4. Pipes
5. Controller Handler
6. Service
7. Interceptors (after)
8. Exception Filters (if error)

🔟 INTERVIEW QUESTIONS & ANSWERS
════════════════════════════════════════════════════════════════════════════════════

Q1: "What's the difference between Guard and Middleware?"
A: "Middleware runs before routing (doesn't know which handler will be called). 
    Guards run after routing (know the exact handler) and have access to ExecutionContext 
    and metadata. Guards are better for authentication/authorization."

Q2: "When would you use an Interceptor vs Middleware?"
A: "Use Middleware for general request handling (logging, CORS). Use Interceptors when 
    you need to modify responses, have access to ExecutionContext, or need RxJS features 
    like caching or timeout handling."

Q3: "How do you test a service with dependencies?"
A: "Use NestJS testing utilities. Create a testing module with Test.createTestingModule(), 
    provide mock dependencies, and inject the service. Example:
    
    const module = await Test.createTestingModule({
      providers: [
        UserService,
        { provide: Database, useValue: mockDatabase }
      ]
    }).compile();
    
    const service = module.get<UserService>(UserService);"

Q4: "What's the difference between @Injectable() and @Inject()?"
A: "@Injectable() marks a CLASS as available for DI (goes on the class definition). 
    @Inject() is used to inject a CUSTOM TOKEN (goes on constructor parameter). 
    Most times you don't need @Inject() - NestJS auto-injects by class type."

Q5: "How does NestJS resolve dependencies?"
A: "NestJS builds a dependency graph at startup. When it creates a class, it looks at 
    constructor parameters, finds matching providers in the module, and injects them. 
    If a dependency has its own dependencies, those are resolved first (recursive)."

Q6: "What's the scope of a provider?"
A: "Three scopes: DEFAULT (singleton - shared across app), REQUEST (new instance per 
    request), TRANSIENT (new instance every time it's injected). Default is most common."

Q7: "How do you share services between modules?"
A: "Export the service in the module where it's defined, then import that module in 
    other modules that need it:
    
    @Module({
      providers: [UserService],
      exports: [UserService]  // ← Export
    })
    
    Then import UserModule in other modules."
