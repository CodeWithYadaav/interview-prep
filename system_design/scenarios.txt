What Questions to Ask if Starting a Project from Scratch?


What kind of questions to ask? Ask questions to understand the exact requirements. Here is a list of questions to help you get started:

What specific features are we going to build?

How many users does the product have?

How fast does the company anticipate to scale up? What are the anticipated scales in 3 months, 6 months, and a year?

What is the company’s technology stack? What existing services you might leverage to simplify the design?

Ronaldo (460M followers) goes live for 1 minute. All followers must be notified INSTANTLY

Functional Requirements:
✅ User goes live → trigger notification to all followers
✅ Multiple notification channels (Push, Email, SMS)
✅ Real-time delivery (< 5 seconds for push, < 1 min for email/SMS)
✅ Stop notifications when live ends
✅ Handle user preferences (don't spam users who disabled notifications)
✅ Deduplication (don't send same notification twice)

Non-Functional Requirements:
✅ Scale: 460M notifications in 1 minute = ~7.6M notifications/second
✅ Low latency: Push notifications < 5 seconds
✅ High availability: 99.99% uptime
✅ Fault tolerance: Handle service failures gracefully
✅ Cost efficient: Don't waste resources on inactive users

STEP 4: DETAILED DATA FLOW (Step by Step)
═══════════════════════════════════════════════════════════════════════════════════

📍 SCENARIO: Ronaldo goes live

Step 1: User Goes Live
──────────────────────
• Ronaldo clicks "Go Live" button in app
• Request → API Gateway → Live Service
• Live Service creates session:
  {
    liveId: "live_123",
    userId: "ronaldo_456",
    status: "active",
    startTime: "2026-01-13T10:00:00Z"
  }
• Store in Redis (fast access) + PostgreSQL (persistence)

Step 2: Publish Live Event
──────────────────────────
• Live Service publishes event to Kafka:
  Topic: "user.went.live"
  Message: {
    liveId: "live_123",
    userId: "ronaldo_456",
    username: "Ronaldo",
    timestamp: "2026-01-13T10:00:00Z"
  }

Step 3: Fan-Out Worker Consumes Event
──────────────────────────────────────
• Fan-Out Worker picks up the event
• Query: "Get all followers of ronaldo_456"
  
  🚨 PROBLEM: Can't fetch 460M records in one query!
  
  ✅ SOLUTION: Pagination + Parallel Processing
  
  • Fetch followers in BATCHES of 10,000
  • Use database sharding (followers split across 100 DB shards)
  • Each shard processed in parallel
  
  Query (on each shard):
    SELECT user_id, notification_preferences 
    FROM followers 
    WHERE following_user_id = 'ronaldo_456' 
    LIMIT 10000 OFFSET 0;

Step 4: Filter & Batch Notifications
─────────────────────────────────────
• For each batch of 10K users:
  - Check Redis cache: Is user online? → Push notification
  - Check preferences: Did user enable notifications? → Filter out
  - Check notification history: Already sent? → Deduplicate
  
• Create notification tasks:
  {
    userId: "user_789",
    liveId: "live_123",
    type: "PUSH", // or EMAIL, SMS
    priority: "HIGH",
    payload: {
      title: "Ronaldo is live!",
      body: "Your favorite creator just went live. Join now!",
      deepLink: "instagram://live/live_123"
    }
  }

Step 5: Push to Notification Queue
───────────────────────────────────
• Fan-Out Worker pushes tasks to Kafka topics:
  - Topic: "notifications.push" (46M messages)
  - Topic: "notifications.email" (200M messages)
  - Topic: "notifications.sms" (214M messages)

Step 6: Notification Workers Process Queue
───────────────────────────────────────────
• Scale horizontally: 1,000+ worker instances
• Each worker consumes 10,000 messages/second
• Total capacity: 1,000 workers × 10K/sec = 10M/second ✅

Push Notification Worker:
  1. Get device tokens from Redis (cached)
  2. Batch 1000 notifications together
  3. Send to Firebase Cloud Messaging (FCM)
  4. FCM delivers to user devices
  5. Log status to Cassandra

Email Worker:
  1. Get email from cache
  2. Batch 500 emails
  3. Send to SendGrid API
  4. Log status

SMS Worker:
  1. Get phone number
  2. Batch 100 SMS
  3. Send to Twilio API
  4. Log status

Step 7: User Goes Offline (Stop Notifications!)
────────────────────────────────────────────────
• Ronaldo clicks "End Live"
• Live Service updates session:
  {
    status: "ended",
    endTime: "2026-01-13T10:01:00Z"
  }
• Publish event: "user.went.offline"
• Workers check Redis before sending:
  if (liveSession.status !== "active") {
    // Don't send notification!
    return;
  }

STEP 5: DATABASE SCHEMA DESIGN
═══════════════════════════════════════════════════════════════════════════════════

1️⃣ Users Table (PostgreSQL - Sharded by user_id)
──────────────────────────────────────────────────
users
  - user_id (PK)
  - username
  - email
  - phone
  - created_at

2️⃣ Followers Table (PostgreSQL - Sharded by following_user_id)
────────────────────────────────────────────────────────────────
followers
  - follower_id (user who follows)
  - following_user_id (user being followed) ← Partition Key!
  - created_at
  - INDEX on following_user_id (for fast lookup)

  Sharding Strategy: Hash-based on following_user_id
  Shard 1: following_user_id % 100 = 0
  Shard 2: following_user_id % 100 = 1
  ...
  Shard 100: following_user_id % 100 = 99

3️⃣ Live Sessions Table (PostgreSQL + Redis)
─────────────────────────────────────────────
live_sessions
  - live_id (PK)
  - user_id
  - status (active, ended)
  - start_time
  - end_time
  - viewer_count

  Redis Cache: Key = "live_session:{live_id}", TTL = 1 hour

4️⃣ User Preferences Table (Redis Cache)
─────────────────────────────────────────
Key: "user_prefs:{user_id}"
Value: {
  "push_enabled": true,
  "email_enabled": false,
  "sms_enabled": false,
  "favorite_creators": ["ronaldo_456", ...]
}
TTL: 24 hours

5️⃣ Notification Logs (Cassandra - Time-series data)
─────────────────────────────────────────────────────
notification_logs
  - notification_id (UUID)
  - user_id
  - live_id
  - type (PUSH/EMAIL/SMS)
  - status (sent, failed, pending)
  - sent_at (timestamp) ← Partition Key
  - created_at

  Partition by: (sent_at_date, user_id)
  Why Cassandra? Handles massive write throughput (460M writes in 1 min)

STEP 6: HANDLING CHALLENGES & EDGE CASES
═══════════════════════════════════════════════════════════════════════════════════

Challenge 1: 460M Database Reads in Seconds 🔥
Solution:
  ✅ Database Sharding (100 shards)
  ✅ Read Replicas (10 replicas per shard = 1000 DB instances)
  ✅ Pagination (fetch 10K at a time)
  ✅ Parallel Processing (1000 workers fetch simultaneously)
  Result: 1000 workers × 10K/sec = 10M reads/sec ✅

Challenge 2: Not All Users Are Active
Solution:
  ✅ Redis cache tracks online users (WebSocket connections)
  ✅ Priority queue: Online users → Push (instant)
  ✅ Lower priority: Offline users → Email/SMS (can be delayed)
  ✅ Smart batching: Group by region/timezone

Challenge 3: Deduplication (Don't Send Twice)
Solution:
  ✅ Redis Set: "notified_users:{live_id}" 
  ✅ Before sending, check: SISMEMBER notified_users:live_123 user_789
  ✅ After sending, add: SADD notified_users:live_123 user_789
  ✅ TTL: 1 hour (auto-cleanup)

Challenge 4: User Goes Offline Mid-Notification
Solution:
  ✅ Workers check Redis before EVERY send:
     if (getLiveSession(liveId).status !== "active") {
       skipNotification();
     }
  ✅ Time-to-Live (TTL) on queue messages (expire after 2 minutes)
  ✅ Dead Letter Queue (DLQ) for failed notifications

Challenge 5: Cost Optimization (414M emails are expensive!)
Solution:
  ✅ Delay email/SMS for 30 seconds (gives push time to reach online users)
  ✅ If user opens app within 30 sec → Cancel email/SMS
  ✅ Use bulk pricing from SendGrid/Twilio
  ✅ Intelligent throttling: VIP users get priority

Challenge 6: Regional Latency (Users in India vs USA)
Solution:
  ✅ Multi-region deployment (AWS regions: US, EU, ASIA)
  ✅ Edge locations for API Gateway (CloudFront)
  ✅ Regional message queues (Kafka clusters per region)
  ✅ Regional notification workers

STEP 7: SCALABILITY & OPTIMIZATION
═══════════════════════════════════════════════════════════════════════════════════

How to Handle 10X More Load? (4.6 Billion followers)
─────────────────────────────────────────────────────
1. Horizontal Scaling:
   • Kafka: Add more partitions (from 100 to 1000)
   • Workers: Scale from 1,000 to 10,000 instances (Auto-scaling)
   • Database: Increase shards from 100 to 500

2. Intelligent Fan-Out:
   • Don't notify ALL followers immediately
   • Priority tiers:
     - Tier 1: Subscribers/VIP fans (instant)
     - Tier 2: Active users (within 10 sec)
     - Tier 3: Inactive users (within 1 min)

3. Pre-computation:
   • Offline job: Pre-compute follower lists for top creators
   • Store in distributed cache (Redis Cluster)
   • Avoid database queries entirely!

4. Rate Limiting:
   • Limit notifications per user (max 5 live notifications/hour)
   • Prevents spam if multiple creators go live

5. Batch Optimization:
   • FCM allows 500 devices per request
   • SendGrid allows 1000 emails per request
   • Use max batch sizes for efficiency

Key Metrics to Track:
• Notification delivery rate (target: > 95% in 5 seconds)
• Queue lag (Kafka consumer lag should be < 1 second)
• Database query time (should be < 100ms per batch)
• Worker CPU/Memory usage
• Failed notification rate (should be < 1%)
• Cost per notification (optimize this!)

Alerts:
🚨 If queue lag > 10 seconds → Auto-scale workers
🚨 If delivery rate < 90% → Page on-call engineer
🚨 If database CPU > 80% → Scale read replicas

STEP 10: INTERVIEW DISCUSSION POINTS
═══════════════════════════════════════════════════════════════════════════════════

What to Say in Interview:

1. "This is a classic fan-out problem - one event triggers millions of notifications"

2. "The key is to decouple event generation from notification delivery using a message queue"

3. "We need to shard the followers database because 460M records can't be fetched in one query"

4. "Push notifications need to be prioritized for online users - they expire quickly"

5. "We should track live session status in Redis to avoid notifying users after stream ends"

6. "Horizontal scaling is critical - we can scale workers independently based on queue depth"

7. "Deduplication prevents sending the same notification twice if there's a retry"

8. "Cost optimization matters - 460M emails are expensive, so we delay and cancel if user is active"

Follow-up Questions They'll Ask:

Q: "What if Kafka goes down?"
A: "Use multiple Kafka clusters with replication. If primary fails, failover to secondary. 
    Also persist events to S3 for recovery."

Q: "How do you handle database hotspots if one celebrity has 500M followers?"
A: "Use consistent hashing for sharding. Add more read replicas for that specific shard. 
    Pre-compute and cache follower lists for top celebrities."

Q: "What if a user's device is offline?"
A: "FCM queues notifications for 4 weeks. When device comes online, it receives pending 
    notifications. We track delivery status in our logs."
